DUALVULNDROID
CHAPTER 02 – LITERATURE REVIEW

## 2.1 Introduction

This chapter reviews the body of prior work relevant to the design of DualVulnDroid. The review is organised around the main technical and conceptual areas that the system draws on: Android application security in general; the two specific vulnerability categories targeted by this research, SQL Injection (CWE-89) and Improper Certificate Validation (CWE-295); static and data-flow analysis; rule-based and signature-based detection; machine learning and deep learning approaches to source-code vulnerability detection; explainable artificial intelligence in cybersecurity; security decision engines that combine multiple sources of evidence; developer-centric security tools and IDE integration; and mobile application security assessment aimed at end users rather than developers. Each area is discussed critically, considering what previous studies and tools actually do, their demonstrated strengths, their acknowledged weaknesses and assumptions, and their relevance to the problem addressed by this research. The chapter closes by drawing these threads together into a critical analysis across the reviewed approaches and a research gap that is built directly from the limitations identified in the literature. This chapter does not describe or evaluate the DualVulnDroid implementation itself; that material is presented in later chapters. Its purpose here is solely to establish, on the basis of existing published work, what has already been done, where the acknowledged limitations lie, and what gap remains to be addressed.

## 2.2 Android Application Security

An Android application is typically composed of components, such as Activities, Services, Broadcast Receivers, and Content Providers, that communicate through the platform's Intent-based messaging system and interact with local storage, background services, and the network. Application security concerns arise wherever this architecture accepts data from a source outside the application's own trust boundary and later uses that data in a security-sensitive operation. The Android Developers documentation identifies several categories of such concerns, including secure handling of data received from other applications or the network, correct use of the permission system, and correct configuration of network communication, particularly Transport Layer Security (TLS) [4]. Two of the recurring attack surfaces in developer-written code are input handling that reaches a local database, and network communication that depends on correct certificate and hostname validation to remain confidential and unmodified in transit.

Database interaction is a long-standing source of injection vulnerabilities across many platforms, not only Android, whenever a query is built by directly combining program logic with data that originates outside the application, rather than through an interface that keeps code and data separate [8], [9]. Network communication introduces a different class of risk: even where TLS is used, an application's own code can silently disable or weaken the certificate and hostname verification that TLS depends on, for reasons that range from convenience during development to a misunderstanding of the relevant API's security-critical semantics [5], [6]. The permission system, meanwhile, controls access to sensitive resources such as location, contacts, and device identifiers, and is a further, related area of academic study, although it is a narrower topic than the two vulnerability categories examined in the rest of this chapter [12], [23]. Taken together, these attack surfaces show that Android application security cannot be reduced to a single concern: input handling, database access, and network trust validation are each governed by their own APIs, their own correct-usage patterns, and their own history of misuse in real applications.

## 2.3 Common Vulnerabilities in Android Applications

Android applications are affected by a broad range of vulnerability classes, including insecure inter-component communication, insecure local data storage, permission misuse, cryptographic misuse, and the two categories of central interest to this research, SQL Injection and Improper Certificate Validation. Industry classifications such as the OWASP Mobile Application Security project group many of these concerns under broader headings such as insecure communication and insufficient input validation, reflecting the fact that individual, narrowly defined weaknesses such as CWE-89 and CWE-295 are specific instances of these broader risk categories rather than unrelated, isolated issues [3].

CWE-89 and CWE-295 are useful as a complementary pair of targets for a detection system for several reasons. First, they represent two structurally different kinds of vulnerability: CWE-89 concerns a data-handling weakness, in which untrusted input reaches a database sink without adequate neutralisation, while CWE-295 concerns a security-configuration weakness, in which an application's own network-trust logic is incorrectly implemented or deliberately weakened [1], [2]. Second, both are well-defined by MITRE's Common Weakness Enumeration, which provides an authoritative, implementation-independent definition of each weakness that is stable across the many different concrete coding patterns that can realise it [1], [2]. Third, both categories have been the subject of substantial, independent empirical study specifically in the Android context: SQL Injection through general static-analysis literature on injection vulnerabilities [8], [9], and Improper Certificate Validation through several large-scale empirical studies of real Android applications [5], [6], [7]. Studying both together, rather than in isolation, allows a detection system to be evaluated on two genuinely different evidentiary structures, one centred on a value's propagation through program logic, the other centred on the correctness of a specific API usage pattern, which is a more demanding and more representative test of a general-purpose approach than either vulnerability alone.

## 2.4 CWE-89 — SQL Injection

MITRE defines CWE-89 as arising when a product constructs all or part of an SQL command using input from an upstream component without correctly neutralising special elements that could change the intended meaning of that command when it reaches the database [1]. The canonical attack mechanism is string concatenation: a query string is built by directly appending untrusted data, such as a value obtained from an Intent extra, a form field, or a network response, into what will become part of the SQL statement text, rather than passing that data separately from the statement's structure. Halfond, Viegas and Orso provide an early and still-cited classification of the different attack techniques that exploit this pattern, together with a discussion of the countermeasures proposed at the time, observing that no single method fully addressed the scope of the problem on its own [8]. The standard, widely recommended remediation is the use of parameterised queries or prepared statements, in which the query structure and the untrusted data are kept separate at the API level, so that the underlying database driver, rather than string concatenation in the application, is responsible for correctly interpreting the data as a literal value.

The mechanism above can be understood in terms of a source, a transformation, and a sink: a source is the point at which potentially untrusted data enters the program, such as an Intent extra; a sink is the point at which that data is used in a security-sensitive operation, such as an Android SQLite database API call; and the transformation is however the data is combined into a query between the source and the sink, for example through direct string concatenation, or, in a safe pattern, only through a placeholder passed to a parameterised query API. Reasoning explicitly about this source-to-sink relationship, an approach broadly associated with static and data-flow analysis literature, allows a detection method to distinguish a case in which untrusted data genuinely reaches an unsafe query construction from a superficially similar case in which the same API is used safely [9], [10].

Existing detection methods for CWE-89 span a spectrum from simple pattern matching, through static and taint/data-flow analysis, to machine-learning-based code classification. Pattern matching, which looks for textual indicators such as string concatenation adjacent to a database call, is inexpensive to implement and easy to explain, but is context-insensitive: it cannot easily distinguish a concatenation that reaches a sink from one that does not, nor can it determine whether the concatenated value is ever influenced by untrusted input, which tends to produce both false positives, where a superficially risky pattern is in fact safe, and false negatives, where an unusual but still vulnerable construction is missed [9]. Static and taint/data-flow analysis, as demonstrated for Android by tools such as FlowDroid, addresses part of this weakness by explicitly modelling how values propagate through a program and by tracking whether a specific source reaches a specific sink, but such analysis is more computationally expensive, depends on an accurate model of the platform's lifecycle and callback structure, and can still be defeated by dynamic or highly indirect constructions that the static model does not capture [10]. Machine-learning-based classification, discussed further in Section 2.8, offers the possibility of learning generalised patterns from labelled examples rather than relying on a fixed rule set, but its effectiveness depends heavily on the quality, size, and diversity of the training data, and a model's prediction alone provides no explicit account of the underlying data flow. No single one of these methods can be said to solve SQL Injection detection in general; each offers a different trade-off between precision, recall, computational cost, and explainability, which is itself part of the motivation for combining more than one form of evidence rather than relying on any single method in isolation.

## 2.5 CWE-295 — Improper Certificate Validation

MITRE defines CWE-295 as occurring when a product does not validate, or incorrectly validates, a certificate, which can allow an attacker to spoof a trusted entity and interfere with the communication path between a client and a server [2]. In the specific case of TLS, correct behaviour requires both that the certificate chain presented by the server is valid and trusted, and that the certificate's identity actually matches the host being connected to, a check normally performed by a HostnameVerifier. Android's own documentation on network protocol security explains that, from Android 9 onward, applications are expected by default to trust only certificates issued by an authority in the standard Android certificate authority set, with any exception required to be declared explicitly through a Network Security Configuration file, precisely because silently weakening this default behaviour in application code is a known source of vulnerability [4].

Two large-scale empirical studies established the practical significance of this vulnerability class in the Android ecosystem. Georgiev et al. examined SSL certificate validation across a range of non-browser software, including several Android applications and libraries, and found that certificate validation was frequently broken due to confusing or misused APIs in the underlying SSL implementations and data-transport libraries [5]. Fahl et al. conducted a large-scale automated and manual analysis of thousands of popular Android applications specifically, introducing the MalloDroid tool to detect potentially vulnerable SSL/TLS usage, and found that a meaningful proportion of examined applications contained code susceptible to man-in-the-middle attacks, with a manual subset confirmed to be practically exploitable [6]. Separately, Egele et al. studied cryptographic API misuse in Android applications more broadly with the CryptoLint tool and found that the large majority of examined applications made at least one cryptographic mistake, illustrating that correct use of security-critical cryptographic and network APIs is difficult for developers to achieve in practice, not merely a theoretical concern [7]. Common insecure patterns identified across this line of work include a HostnameVerifier whose verify method unconditionally returns true, and a TrustManager whose checkServerTrusted or checkClientTrusted method is implemented with an empty body, both of which disable the very checks the API exists to perform.

Detection approaches for this vulnerability class include static pattern detection for the specific unsafe method-body shapes described above, semantic and API-aware analysis that considers how a HostnameVerifier or TrustManager implementation is actually constructed and used, and, more recently, machine-learning approaches applied to the surrounding code context. API-pattern detection benefits from the fact that the vulnerable shapes are relatively well understood and can be defined precisely, for example an empty or trivially-true method body, which supports high-confidence, low-noise detection when the pattern is present exactly as expected. Its principal limitation, however, is that the security-relevant behaviour is not always confined to a single, easily located method: validation logic can be spread across several methods or classes, delegated conditionally, or combined with other checks elsewhere in the code, and a detector limited to a narrow, single-method pattern may either miss such distributed cases, producing a false negative, or flag code whose surrounding context in fact renders it safe, producing a false positive, if that context is not considered together with the local pattern.

## 2.6 Static Analysis and Data-Flow Analysis

Static analysis examines a program's source code or compiled representation without executing it. At its simplest, lexical analysis operates directly on the token stream of the source text, for example matching a specific method name or literal pattern; abstract-syntax-tree (AST) based analysis instead operates on the parsed structure of the code, which allows a tool to distinguish, for example, a genuine method call from a similarly-named string literal; and control-flow analysis reasons about the possible order in which statements can execute. Data-flow analysis, and its security-focused specialisation taint analysis, builds on these foundations to reason about how values move through a program: a source is a point where a value of interest, often untrusted input, is introduced; a sink is a point where that value is used in a way that matters for correctness or security; propagation describes how a value travels between statements, methods, and, in interprocedural analysis, across function or component boundaries; and sanitisation or parameterisation describes an operation that renders a value safe to reach a sink that would otherwise be dangerous, for example replacing an unsafe concatenated query with a parameterised one.

FlowDroid is a widely cited example of precise, static taint analysis specifically for Android applications, explicitly modelling the platform's component lifecycle and callback structure in order to track information flow with greater precision than earlier, coarser approaches, while TaintDroid demonstrated a complementary, dynamic approach that tracks tainted data at runtime on the device itself rather than through static modelling [10], [11]. Data-flow evidence of this kind is a natural complement to machine-learning classification: where a classifier produces a prediction and, at best, an indication of which input features contributed to it, a source-to-sink trace produced by data-flow analysis provides a concrete, independently checkable account of why a specific piece of code is considered risky, namely that a specific value from a specific source demonstrably reaches a specific sink without an intervening safe transformation. This evidentiary property is difficult for a purely statistical model to reproduce on its own.

At the same time, the literature is candid about the limitations of static and data-flow analysis. Precise interprocedural analysis is computationally expensive and can scale poorly to large codebases, which creates pressure to adopt coarser approximations that in turn reduce precision, as FlowDroid's own motivation notes with respect to prior Android taint-analysis tools [10]. Coverage of a specific programming language or set of APIs must be maintained deliberately, since the analysis is only as complete as its model of the platform and libraries in use, and unmodelled APIs or reflection-based and dynamically constructed code can cause a source-to-sink path to be missed entirely. Finally, even precise data-flow analysis is not immune to false positives, since a path that is technically reachable according to the model may in practice be infeasible, guarded by a runtime condition, or otherwise never actually exploitable, a well-known general challenge for static analysis tools discussed further in Section 2.12.

## 2.7 Rule-Based and Signature-Based Detection

Rule-based and signature-based approaches detect vulnerabilities by matching code against a predefined set of deterministic conditions: specific API signatures known to be dangerous, specific code patterns such as an unconditionally-true return statement inside a particular method shape, or regular expressions over the source text. This style of detection has a long history in both academic and commercial static-analysis tools and remains widely used because of several concrete advantages. Findings produced by a fixed rule are directly explainable, since the rule itself states exactly what condition was matched; behaviour is deterministic and reproducible, given the same input; the computational cost of evaluating a fixed set of rules is generally low compared with more sophisticated analyses; and the correctness of an individual rule is comparatively easy to validate in isolation, since its intended scope is narrow and explicit.

These advantages are balanced by well-documented limitations. Rules defined around a specific syntactic shape are brittle: a semantically equivalent but syntactically different variant of the same vulnerable pattern, for example an equivalent construction expressed with a different set of intermediate variables, can silently evade a rule that was written for a narrower shape. Because each rule targets a specific, known pattern, rule sets generalise poorly to variants that were not anticipated when the rule was written, which requires ongoing maintenance effort to keep pace with new coding idioms and framework changes. Perhaps most importantly for the purposes of this research, deterministic rules by themselves capture only the presence of a pattern, not the broader contextual relationships, such as whether a value genuinely originates from an untrusted source before reaching a matched sink, that determine whether the pattern is actually exploitable in a given piece of code. This is precisely the gap that motivates combining deterministic rule or data-flow evidence with a learned model: the rule or data-flow component contributes explainable, low-cost, high-confidence evidence for the specific patterns it is designed to recognise, while a learned component can contribute broader generalisation across coding styles that were not explicitly anticipated, at the cost of the model's own limitations discussed in the next two sections.

## 2.8 Machine Learning for Source-Code Vulnerability Detection

Classical machine-learning approaches to source-code vulnerability detection typically represent code as a feature vector and train a supervised classifier to distinguish vulnerable from safe examples. Common feature representations include lexical features derived from tokenised source text, such as term-frequency--inverse-document-frequency (TF-IDF) weighted n-grams, structural features derived from the code's syntax or control structure, general code metrics such as size or complexity, and security-specific features constructed to capture domain knowledge directly, for example the presence of a known-dangerous API call or a known-safe parameterised pattern. Classifiers commonly applied to such feature representations include Support Vector Machines (SVM), whose foundational formulation was introduced by Cortes and Vapnik as a general-purpose approach to binary classification through an optimal separating hyperplane [13]; Random Forest, an ensemble of decision trees introduced by Breiman that averages the predictions of many trees trained on randomly sampled subsets of the data and features [14]; and gradient-boosted tree ensembles such as XGBoost, a scalable implementation of tree boosting introduced by Chen and Guestrin that has become widely used across many applied machine-learning tasks because of its strong empirical performance and efficient training [15].

These classical approaches offer several advantages relevant to vulnerability detection. They can, in principle, scale to large volumes of labelled examples more readily than exhaustive manual rule authoring; they are capable of learning patterns that were not explicitly anticipated by a human rule author, provided such patterns are present with sufficient consistency in the training data; and feature-engineered approaches in particular allow domain knowledge, such as the security-specific features described above, to be combined directly with more general lexical or structural signals within a single model.

At the same time, the literature and general machine-learning practice identify a number of important limitations that apply to this style of approach regardless of the specific classifier used. Model performance is fundamentally dependent on the quality of the underlying dataset: label noise, in which a training example is incorrectly or inconsistently labelled, and class imbalance, in which one class is substantially over- or under-represented relative to the other, can both bias a trained model's behaviour in ways that are not obvious from aggregate accuracy figures alone. Data leakage, in which information that would not be available at genuine prediction time is inadvertently made available during training or evaluation, for example through near-duplicate examples appearing on both sides of a train/test split, can produce evaluation results that substantially overstate real-world performance. The specific feature representation chosen also constrains what a model can learn: a purely lexical representation, for instance, cannot directly encode a source-to-sink relationship unless that relationship is captured by a dedicated, deliberately engineered feature. Finally, models trained and evaluated on isolated code snippets face an open question of generalisation to genuinely new, unseen applications, since a dataset assembled from a finite set of source applications or templates may not fully represent the diversity of real-world code, and, as with any binary classifier applied to a security task, a trained model will exhibit some rate of false negatives that must be measured and reported rather than assumed away. This chapter does not report specific measured figures for any model; such results are presented later, in the chapters concerned with model development and evaluation and with results and discussion.

## 2.9 Deep Learning for Source-Code Vulnerability Detection

Deep-learning approaches to source-code vulnerability detection extend the classical feature-engineered paradigm by learning a representation of code directly from token or character sequences, rather than relying on hand-designed features. Sequence models such as recurrent neural networks and, in particular, Long Short-Term Memory (LSTM) networks have been applied to model code as a sequence of tokens, learning to recognise patterns associated with vulnerable code from labelled sequences of this kind; VulDeePecker is a widely cited example of this style of approach, using a deep-learning pipeline built around code sequences derived from program slices to detect vulnerable functions [16]. More recently, Transformer-based models pretrained on large corpora of source code have been applied to code-understanding tasks; CodeBERT, introduced by Feng et al., is a bimodal Transformer model pretrained jointly on natural language and programming language data, intended to support a range of downstream tasks that require understanding the relationship between code and natural language or between different pieces of code [17].

A key distinction relevant to this research is between models trained entirely from scratch on a specific, often comparatively small, labelled dataset, such as a from-scratch LSTM, and models such as CodeBERT that begin from parameters pretrained on a very large, general corpus of code before being fine-tuned on a smaller, task-specific labelled dataset. Pretrained models of this kind bring prior knowledge of general code structure and common idioms into the fine-tuning process, which can be particularly valuable when the task-specific labelled dataset is modest in size, whereas a from-scratch sequence model must learn both general code structure and the specific task from the same limited labelled data, which increases its risk of overfitting to that data. Deep-learning approaches in general also carry a materially higher computational cost for training and inference than the classical models discussed in Section 2.8, and their internal representations are considerably less directly interpretable, a point returned to in Section 2.10.

It is important not to overstate the advantage of deep learning in this setting. Whether a deep-learning approach outperforms a well-engineered classical model is an empirical question that depends heavily on the size and quality of the available labelled dataset, the specific task, and the chosen representation; feature-engineered classical models remain competitive baselines in the vulnerability-detection literature, and a pretrained model's advantage from general code knowledge does not automatically translate into superior performance on a specific downstream task with a limited amount of labelled fine-tuning data. This research therefore treats deep-learning models as an empirical comparison to be evaluated against classical models under a shared protocol, discussed in Chapter 6, rather than assuming in advance that either family of approaches is superior.

## 2.10 Explainable AI for Cybersecurity

A recurring theme in the machine-learning literature is the tension between model accuracy and model interpretability: the models that most often achieve the strongest predictive performance, such as ensemble tree methods and deep neural networks, are also typically the hardest for a human to inspect and understand directly [19]. This tension is particularly consequential in a security context, where a model's output is not simply consumed for its own sake but is used to justify a subsequent action, whether that action is a developer deciding whether to change a specific line of code, a security analyst deciding whether a finding merits further investigation, or an end user deciding whether to install or continue using an application. Ribeiro, Singh and Guestrin motivate this need directly, arguing that understanding the reasons behind a prediction is important for assessing whether to trust that prediction and any action taken as a result of it, and propose Local Interpretable Model-Agnostic Explanations (LIME) as one solution, approximating a complex model's local behaviour around a specific prediction with a simpler, interpretable model [20]. Lundberg and Lee take a related but distinct approach with SHapley Additive exPlanations (SHAP), unifying a family of additive feature-attribution methods within a single framework with a set of desirable theoretical properties, and assigning each input feature a value representing its contribution to a specific prediction [19].

Feature-attribution methods of this kind provide a model-level explanation: they describe which input features most influenced a specific model output, according to the model's own learned behaviour. This is a genuinely useful and, at the level of an individual prediction, mathematically grounded form of explanation, but it is not the same thing as an independently verifiable account of why the underlying code is actually vulnerable. A feature attribution can indicate that certain tokens or structural elements were influential in the model's decision without stating, for example, that a specific value demonstrably reaches a specific dangerous sink; that latter kind of account is instead the province of the rule and data-flow evidence discussed in Sections 2.6 and 2.7. The literature on explainability in security-relevant machine learning has, in some cases, combined the two: Arp et al.'s DREBIN, for example, is explicitly designed to be explainable as well as effective, deriving its explanations directly from a linear model over a large set of manually defined, security-relevant features, illustrating one way of keeping a model's explanation closely tied to concrete, human-meaningful evidence [18]. This distinction between a model's own internal explanation and independently verifiable rule- or data-flow-based evidence is important to maintain clearly, rather than conflating the two, since they answer related but different questions and carry different guarantees.

## 2.11 Security Decision Engines and Evidence-Based Decision Support

A binary classification output, vulnerable or safe, is a narrow basis for a practical security decision on its own. A classifier's confidence score reflects the model's own internal certainty given its learned parameters and its training distribution, but it does not, by itself, indicate whether independent, verifiable evidence supports the same conclusion, nor does it indicate how the classifier is likely to behave on cases that differ from its training distribution. This observation motivates a broader class of approaches that combine a machine-learning prediction with other sources of evidence, such as static analysis findings, rule-based signals, or explicit confidence thresholds, before arriving at a final decision, an idea closely related to defence-in-depth and multi-signal approaches more generally discussed in the static and dynamic analysis literature reviewed above [10], [18].

A central design question for any such combined system is how to allocate decisions between full automation and human review. A system that is tuned to decide every case automatically, without deferring any case for manual attention, necessarily accepts whatever error rate its automatic decisions carry across the full range of inputs it encounters, including the cases where its available evidence is genuinely weak or contradictory. A system that instead explicitly represents uncertainty, deferring cases where the available evidence does not clearly support one conclusion to manual review while deciding confidently supported cases automatically, introduces a further trade-off between coverage, the proportion of cases decided automatically, and the reliability of those automatic decisions, typically measured through metrics such as false positive and false negative rates restricted to the automatically decided cases. Higher coverage generally comes at the cost of including more borderline cases in the automatically decided set, which tends to reduce the reliability of that set, while a more conservative, lower-coverage configuration can achieve higher reliability on the cases it does decide automatically at the cost of deferring a larger proportion of cases to manual review. Balancing automation and manual review in this way, rather than presenting every prediction as an equally confident, automatic verdict, is a recurring concern in the broader literature on practical, evidence-based decision support, and is the general concept this research draws on; the specific decision-engine design used in DualVulnDroid, and its own measured coverage and reliability trade-offs, are presented later in this thesis and are not claimed as an established finding of the literature reviewed here.

## 2.12 Developer-Centric Security Tools and IDE Integration

A separate strand of literature examines not the underlying detection technique but how security and static-analysis tools are actually used, or not used, by developers in practice. Johnson et al. interviewed professional developers about their use of static analysis tools and found that, although developers generally regarded such tools as beneficial in principle, false positives and the manner in which warnings were presented were significant barriers to sustained use [21]. Christakis and Bird conducted a related empirical study specifically on what developers want and need from program analysis tools, finding that developers particularly value tools that integrate closely with their existing workflow, minimise interruptions, and maintain a low false-positive rate, and that unclear warning messages and slow tool performance actively discourage adoption [22]. Taken together, this line of work indicates that the perceived usability of a developer security tool, encompassing the latency of feedback, the clarity of the explanation provided with a finding, and the tool's integration into the developer's normal editing workflow, is at least as important to real-world effectiveness as the underlying detection technique's raw accuracy.

Real-time, editor-integrated feedback, in which a potential issue is flagged as the developer writes the corresponding code rather than during a separate, later scanning step, is one response to this usability concern, since it shortens the feedback loop between introducing an issue and becoming aware of it. Inline annotations and IDE inspections of this kind, together with project-wide scanning for a fuller pass over an existing codebase, and offering a scoped, verifiable automatic remediation such as a quick fix where a finding matches a pattern that can be safely and narrowly corrected, are recurring features associated with developer-centric tooling more broadly. The same literature that documents the value of these features, however, also documents concrete risks associated with them: latency in providing feedback erodes trust in the same way that a delayed compiler error would; a high volume of low-value warnings produces alert fatigue, in which developers begin to ignore a tool's output altogether, a failure mode explicitly identified as a barrier to adoption [21]; and an automatic remediation applied without sufficiently narrow scoping or without re-verification after the change risks introducing new defects while attempting to fix an existing one. These are not claims that existing developer-centric tools are ineffective in general; rather, the literature identifies specific, well-documented conditions, response latency, warning clarity, false-positive rate, and remediation safety, under which such tools succeed or fail to be adopted and used effectively in practice.

## 2.13 Mobile Application Security Assessment for End Users

The literature discussed so far is concerned primarily with helping a developer identify and correct vulnerabilities in code that they themselves are writing or maintaining. A related but distinct body of work is concerned with helping an end user, who does not write or read the application's source code, make an informed decision about whether to install or continue using an already-published application. APK-level analysis, including manifest analysis of declared permissions, components, and requested SDK versions, provides the technical basis for this kind of assessment, since it can be performed on a compiled application package without access to its original source code.

Felt et al.'s empirical study of how users actually attend to and comprehend Android permission requests is directly relevant here: the study found generally low rates of user attention and comprehension of permission warnings presented in the platform's own installation-time interface, with only a minority of surveyed users reporting that they paid attention to permissions at all, although a smaller group did demonstrate meaningful awareness and comprehension [23]. This finding illustrates a broader gap between the technical output that an analysis produces, such as a list of requested permissions or a raw vulnerability finding, and an end user's practical ability to interpret that output and act on it appropriately. It supports the view, echoed across usable-security research more generally, that raw technical findings are not, by themselves, an effective form of risk communication for a non-expert audience, and that understandable, consequence-oriented recommendations, together with contextual information such as whether a given application is actually compatible with the user's own device, are necessary to bridge the gap between developer-facing security analysis and genuinely useful, user-facing security decision support. This distinction between developer-oriented and user-oriented security information is treated in this research as two related but separate outputs that must each be designed for their intended audience, rather than a single technical finding presented unchanged to both.

## 2.15 Critical Analysis of Existing Approaches

Reviewing the studies above together, several trade-offs recur across, rather than within, individual categories of approach. Pattern-based and rule-based detection (Sections 2.4, 2.5, 2.7) offers strong explainability, deterministic behaviour, and low computational cost, but is fundamentally limited in recall against pattern variants it was not designed to recognise, and offers no account of contextual reachability on its own. Static and data-flow analysis (Sections 2.4–2.6) improves on this by modelling how values actually propagate through a program, providing genuinely verifiable source-to-sink evidence, but at a materially higher computational cost, with precision that depends on the completeness of the underlying platform and API model, and with acknowledged scalability limits for large, complex, or dynamically constructed codebases [10]. Classical machine learning (Sections 2.8, 2.14) trades the need for hand-authored rules for the need for a labelled dataset, and can generalise across coding styles that a fixed rule set does not anticipate, but its effectiveness is bounded by dataset quality, label noise, and class balance, and its raw predictions carry no explicit contextual evidence of their own [13], [14], [15]. Deep learning (Section 2.9) extends this further by learning representations directly from code sequences, and pretrained models such as CodeBERT bring general code knowledge that can be valuable when labelled data is limited, but at a higher computational cost, with reduced interpretability, and without a general guarantee of superiority over well-engineered classical models on a specific, comparatively small task-specific dataset [16], [17].

Explainable AI methods such as SHAP and LIME (Sections 2.10, 2.14) address part of the interpretability gap left by classical and deep-learning models, but they explain a model's own behaviour, not an independently verifiable fact about the code, a distinction this review has been careful to maintain rather than treat model-level explanation and rule- or data-flow-based evidence as interchangeable [19], [20]. Developer-integrated tools (Section 2.12) improve the practical usability of any of the above detection techniques by shortening the feedback loop and situating findings within the developer's normal workflow, but the same literature that motivates this integration also documents that poor false-positive rates, unclear explanations, and high latency actively undermine adoption regardless of the underlying technique's accuracy [21], [22]. Finally, user-facing security decision support (Section 2.13) is comparatively underexplored relative to developer-facing analysis in the reviewed literature, and the available evidence suggests that raw technical findings are a poor substitute for understandable, consequence-oriented recommendations when the intended audience is a non-expert end user rather than a developer [23].

Across all of these categories, several limitations recur consistently: a tendency to treat detection accuracy in isolation from the coverage/reliability trade-off that determines whether an automatic decision is actually trustworthy (Section 2.11); a tendency to evaluate detection techniques on a single vulnerability category rather than multiple, structurally different categories together; and a general scarcity of published work that evaluates model-level explanation, rule- or data-flow-based evidence, developer-facing presentation, and end-user-facing presentation within a single, coherently integrated system, rather than as separate, independently studied concerns.

## 2.16 Research Gap Identification

The preceding sections support several specific, evidence-based observations about the current state of the literature. Studies of CWE-89 detection and studies of CWE-295 detection in Android applications are, in the literature reviewed here, conducted largely independently of one another, using different techniques and different evaluation datasets, rather than being addressed together within a single evaluated system [5], [6], [7], [8], [9], [10]. Much of the classical and deep-learning vulnerability-detection literature evaluates a learned model's predictive performance without an explicit, integrated account of static or data-flow evidence alongside it, leaving the model's raw prediction as the primary basis for a detection decision [13]–[17]. The explainability literature, while providing genuine model-level attribution methods, is generally studied separately from the rule- and data-flow-evidence literature, rather than the two being combined and clearly distinguished from one another within one system [19], [20]. The developer-tool-adoption literature identifies concrete usability requirements, workflow integration, low false-positive rates, and response latency, that are treated as properties of the tool's presentation layer rather than requirements engineered into the detection pipeline itself [21], [22]. Finally, the end-user-facing security literature that does exist indicates a genuine gap between raw technical findings and comprehensible risk communication, and is largely separate from the developer-facing source-code-analysis literature reviewed in the earlier sections of this chapter [23].

These observations are stated here as candidate gaps supported specifically by the literature discussed above; they are not claims that no system anywhere addresses any of these concerns, nor are they claims that DualVulnDroid is unique simply by virtue of combining existing techniques. Table 2.2 summarises each identified gap, the literature evidence supporting it, and, narrowly, what DualVulnDroid as implemented in this research actually addresses in relation to it.

**Table 2.2. Research gap summary.**

| Identified Gap | Evidence from Literature | How DualVulnDroid Addresses It |
|---|---|---|
| CWE-89 and CWE-295 are typically studied and detected as separate problems. | Distinct, largely non-overlapping bodies of work for SQLi detection [8], [9] and Android SSL/certificate misuse [5], [6], [7]. | Implements detection, evidence, and decision support for both CWE-89 and CWE-295 within a single, shared pipeline and evaluation protocol. |
| Machine-learning vulnerability detection is often evaluated without integrated static/data-flow evidence alongside the model prediction. | Classical/deep-learning studies report predictive performance as the primary result [13]–[17]. | Combines the trained classifier's prediction with deterministic static and data-flow evidence in a single Decision Engine, rather than relying on the model prediction alone. |
| Model-level explanation (e.g. SHAP/LIME) and rule/data-flow evidence are studied separately and are not always clearly distinguished. | XAI literature focuses on explaining model behaviour [19], [20]; data-flow literature focuses on verifiable propagation evidence [10], [11]. | Surfaces SHAP-based model explanation and source-to-sink/rule evidence as two distinct, separately labelled outputs for the same finding. |
| Developer-tool usability requirements (low false positives, workflow integration, response latency) are documented but not always engineered directly into the detection pipeline. | Empirical studies of developer tool adoption identify these as barriers when absent [21], [22]. | Provides real-time, in-editor annotation, a bounded and independently re-verified Quick Fix mechanism, and project-wide scanning integrated into the IDE workflow. |

| End-user-facing security decision support is comparatively underexplored relative to developer-facing analysis, and raw findings are known to be poorly understood by non-expert users. | Empirical evidence of low user attention/comprehension of raw security information [23]. | Provides a separate, plain-language, user-oriented application offering assessment, compatibility information, and alternatives, distinct from the developer-facing plugin output. |

Two candidate gap areas considered during this review are deliberately not claimed here. First, whether hybrid machine-learning-plus-deterministic-evidence decision making is, in general, an underexplored practical integration point across the security literature as a whole is a broader claim than the literature specifically reviewed in this chapter can support; this chapter therefore limits its claim to the narrower, evidenced points listed in Table 2.2 rather than asserting a sweeping generalisation about the field. Second, this review did not identify a study that evaluates integrated compatibility analysis alongside a security recommendation for the same application in the specific way later implemented in this research; this is noted as an area where the available literature evidence was limited rather than as an established, independently documented gap, and is discussed further as a limitation of this review in Section 2.17.

## 2.17 Summary

This chapter has reviewed the literature underlying Android application security, the two specific vulnerability categories addressed by this research, CWE-89 and CWE-295, and the major technical approaches available for detecting and reasoning about them: rule-based and signature-based detection, static and data-flow analysis, classical machine learning, deep learning, explainable AI, evidence-based decision support, developer-centric tooling, and end-user-facing mobile security assessment. Across these areas, a consistent theme emerges: each individual technique offers real, evidenced strengths together with real, evidenced limitations, and no single technique reviewed here is shown in the literature to solve vulnerability detection, explanation, or decision support on its own. Rule-based and static analysis provide explainable, verifiable evidence but limited generalisation; classical and deep machine learning provide broader generalisation but limited built-in explainability and a dependence on dataset quality; explainability techniques illuminate model behaviour without independently verifying the underlying code; and developer- and user-facing tooling research shows that technical accuracy alone does not guarantee that a tool's output is understood or acted upon by its intended audience.

From this review, a specific, literature-supported research gap has been identified: the absence, in the reviewed literature, of a system that jointly addresses CWE-89 and CWE-295 detection, combines machine-learning prediction with explicit static/data-flow evidence and model-level explanation, engineers developer-tool usability requirements directly into a real-time IDE-integrated workflow, reports the coverage/reliability trade-off of its automated decisions explicitly, and separately provides comprehensible, user-facing security decision support alongside developer-facing analysis. This gap, built directly from the specific limitations discussed above and summarised in Table 2.2, is the gap this research addresses. The following chapter, Chapter 3 — Methodology, describes the research methodology adopted to address this gap, including dataset preparation, feature engineering, model training and comparison, decision-engine design, and the approach taken to production integration and validation.
