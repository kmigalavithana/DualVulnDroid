DUALVULNDROID
CHAPTER 01 – INTRODUCTION

## 1.1 Background

Android remains the most widely used mobile operating system in the world, and the number of applications published for the platform continues to grow every year [Reference required: Android market share and application growth statistics]. As mobile applications increasingly handle sensitive tasks such as authentication, financial transactions, and personal data storage, the security of the code running on Android devices has become a critical concern for developers, organisations, and end users alike. A single vulnerability in a widely distributed application can expose millions of users to data theft, financial loss, or unauthorised access to their devices.

Among the many categories of security weaknesses that affect Android applications, two recur with particular frequency in developer-written code: SQL Injection (CWE-89) and Improper Certificate Validation (CWE-295). SQL Injection arises when untrusted input, such as data obtained from an Intent, a network response, or a user interface element, is concatenated directly into a SQL query instead of being passed through a parameterised interface. When this occurs, an attacker who controls the input can alter the meaning of the query, potentially reading, modifying, or deleting data that the application was never intended to expose. Improper Certificate Validation, by contrast, is a network-layer weakness in which an application's TLS/SSL certificate or hostname verification logic is bypassed or weakened, for example through a HostnameVerifier that always returns true or a TrustManager whose validation method is left empty. This class of vulnerability allows an attacker positioned on the same network, such as a malicious public Wi-Fi hotspot, to intercept or tamper with traffic that the application believes to be secure.

Both vulnerability types share a common characteristic: they are introduced by specific, recognisable coding patterns, yet they are not always obvious to the developer at the moment the code is written. Traditional approaches to catching such issues have relied heavily on manual code review and static, rule-based scanning tools. Manual review is time-consuming, inconsistent between reviewers, and difficult to scale across large codebases or fast-moving development schedules. Purely rule-based detection, meanwhile, tends to rely on fixed keyword or pattern matches, which can be effective for a small number of well-known anti-patterns but struggle to account for the surrounding context of a piece of code, such as whether a variable is genuinely derived from an untrusted source or whether it eventually reaches a dangerous sink. As a result, rule-based tools are prone to both missed detections and a high rate of findings that do not represent a genuine risk, which in turn causes developers to lose trust in the tool and ignore its output.

Identifying vulnerabilities earlier in the software development lifecycle, ideally while the developer is still writing the code, is widely recognised as more effective and less costly than discovering the same issues later during testing, code review, or, worse, after the application has already been released. This has motivated growing interest in combining machine learning with traditional static and data-flow analysis: machine learning models can learn patterns from labelled examples of vulnerable and safe code that may be difficult to express as a fixed set of rules, while data-flow analysis can supply concrete, verifiable evidence, such as the actual path a value takes from an untrusted source to a sensitive sink, that a rule or a model prediction alone cannot provide. Neither approach is sufficient in isolation. A machine learning model without supporting evidence offers little more than a confidence score, which is difficult for a developer to act on or trust; a purely rule-based system without any learned generalisation is brittle and easily bypassed by even minor variations in coding style.

There is also a broader need that goes beyond detection alone. A security tool that simply labels a piece of code as "vulnerable" or "safe" gives the developer little guidance on why the finding was made, how confident the system is, or what should be done about it. Similarly, from the perspective of a person deciding whether to install an already-published application, a binary safe/unsafe verdict is of limited practical use without an explanation of the underlying risk, an indication of whether the application is even compatible with the user's device, and, where appropriate, a safer alternative to consider. This points to a need for systems that move beyond binary detection toward genuine security decision support: combining a prediction with explainable evidence, a transparent decision process, and actionable guidance for the specific audience consuming the result, whether that audience is a developer writing code or a user deciding whether to install an application.

It is this combination of requirements, detection of both CWE-89 and CWE-295, evidence-based explainability, real-time developer support, and user-oriented security assessment, that motivates the system developed in this research: DualVulnDroid. DualVulnDroid is an integrated Android security analysis system consisting of a real-time IntelliJ/Android Studio developer plugin, a FastAPI backend built around a machine-learning classification pipeline and a Hybrid Decision Engine, and a Flutter-based end-user application that allows a person to search for an application, review its security assessment, check its compatibility with their device, and consult a security-focused chatbot. The machine-learning component of DualVulnDroid was evaluated across several candidate models, and XGBoost was selected as the production classifier based on the combined research evaluation, its existing explainability support through SHAP, and its established integration with the backend and the developer plugin. The remainder of this chapter defines the problem this research addresses, states the aim and objectives of the work, lists the research questions investigated, defines the scope of the study, discusses its significance, and outlines the structure of the remainder of the thesis.

## 1.2 Problem Statement

Many existing approaches to Android vulnerability detection address SQL Injection and Improper Certificate Validation, when they address them at all, as separate, isolated problems, typically supported by different tools, different rule sets, or different research efforts. This separation makes it difficult to offer a developer or a user a single, consistent security assessment that covers both vulnerability types together. Traditional approaches may also rely primarily on simple pattern or keyword matching, which can flag the presence of a risky-looking API call without verifying whether untrusted data genuinely reaches that call, and without providing the surrounding contextual or data-flow evidence that would allow a developer to judge whether a finding is a real risk or a false alarm.

A further limitation of many existing tools is limited explainability. A finding reported as a bare label or a numeric score gives little indication of why the underlying model or rule reached that conclusion, which makes it harder for a developer to trust, verify, or act on the result. Where explainability is offered, it is often restricted to either the model's internal reasoning or a static rule description, rather than combining the two into a single, coherent account of the evidence behind a decision. In addition, many detection tools are not integrated into the developer's real-time workflow; they are run as a separate, manually triggered scanning step, which reduces the likelihood that a vulnerability is corrected before it is committed to the codebase.

From the perspective of an end user rather than a developer, an identifiable gap is the general lack of user-oriented security decision support for already-published Android applications. Existing app stores and general-purpose security scanners rarely provide an accessible, plain-language explanation of why an application has been flagged as risky, whether the application is actually compatible with the user's specific device, or what safer alternatives might exist in the same category. Remediation guidance, where it exists at all, is often generic rather than tied to the specific vulnerable pattern that was detected, and automated code fixes are rarely offered with enough care to guarantee that only the intended, verified vulnerable pattern is modified.

Finally, any system that attempts automatic detection and decision-making faces an inherent tension between coverage and reliability: a system tuned to flag every possible case will produce a large number of false positives and erode developer trust, while a system tuned to minimise false positives risks silently missing genuine vulnerabilities. These limitations motivate a system that treats coverage and reliability as parameters to be measured and reported honestly, deferring uncertain cases to manual review rather than forcing an automatic verdict in every case.

These limitations motivate the specific gap addressed by this research: the absence of a single, integrated system that combines machine-learning-based classification of both CWE-89 and CWE-295, deterministic static and data-flow evidence, an explainable and transparent decision process, real-time developer support, and user-oriented security assessment, compatibility checking, and remediation guidance, within one coherent architecture. DualVulnDroid is designed to address this gap.

## 1.3 Research Aim

The aim of this research is to design, develop and evaluate DualVulnDroid as an integrated Android security analysis and decision-support system capable of detecting CWE-89 (SQL Injection) and CWE-295 (Improper Certificate Validation) using machine learning together with static and data-flow evidence, while providing explainability, remediation support, and user-oriented security information to both developers and end users.

## 1.4 Research Objectives

The following objectives were pursued in order to achieve the research aim stated above:

1. To investigate the detection requirements for CWE-89 and CWE-295 in Android application code, including the specific coding patterns, data-flow characteristics, and contextual evidence associated with each vulnerability type.
2. To prepare, clean, and validate a labelled dataset of vulnerable and safe code samples suitable for training and evaluating machine-learning classifiers, including the identification and removal of conflicting or duplicated labels.
3. To design and implement a feature-engineered machine-learning pipeline, combining text-based features with deterministic security- and data-flow-derived features, for classifying Android code as vulnerable or safe.
4. To train and compare classical machine-learning models, specifically Support Vector Machines, Random Forest, and XGBoost, on the prepared dataset under an identical evaluation protocol.
5. To evaluate deep-learning approaches, specifically an LSTM-based sequence model and a fine-tuned CodeBERT transformer model, as supplementary research comparisons against the classical machine-learning models.
6. To develop and integrate deterministic static and data-flow analysis capable of tracing a value from a potential source to a potential sink, and to use this evidence alongside the machine-learning prediction.
7. To select a production classifier from the evaluated models and integrate it with an explainable Hybrid Decision Engine that combines the model prediction, the static and data-flow evidence, and SHAP-based explanation into a single, transparent decision.
8. To design and implement a real-time developer plugin for IntelliJ-based IDEs, providing in-editor vulnerability annotation, a detail view, project-wide scanning, and Quick Fix support for verified safe remediation patterns.
9. To design and implement a Flutter-based, user-oriented application providing application security assessment, device compatibility checking, alternative application recommendations, and a security-focused chatbot grounded in real backend data.
10. To evaluate the completed system through automated testing of its individual components and through validation in real execution environments, including a real IntelliJ Platform test fixture and a real Android emulator.

## 1.5 Research Questions

This research was guided by the following research questions:

**RQ1.** How effectively can machine learning techniques detect CWE-89 and CWE-295 vulnerabilities in Android code?

**RQ2.** How do Support Vector Machines, Random Forest, and XGBoost compare in vulnerability classification performance?

**RQ3.** Can deep-learning approaches such as LSTM and CodeBERT provide useful performance compared with classical machine-learning approaches on this task?

**RQ4.** How can static and data-flow evidence be combined with machine-learning predictions to support more security-aware decisions than either source of evidence could provide alone?

**RQ5.** How effectively can explainable evidence, such as SHAP feature contributions and source-to-sink data-flow information, support developer understanding of vulnerability findings?

**RQ6.** How can DualVulnDroid provide both developer-oriented, real-time vulnerability detection and user-oriented security decision support within a single system?

**RQ7.** How effectively can the system support APK security assessment, device compatibility analysis, and alternative application recommendations for end users?

## 1.6 Scope of the Research

This research is concerned with the detection of two specific vulnerability categories in Android application source code, CWE-89 (SQL Injection) and CWE-295 (Improper Certificate Validation), and with the design of a system that supports both developers and end users in understanding and acting on findings related to these two categories. The scope of the research includes: static and data-flow analysis of Java and Kotlin source code, to the extent supported by the developer plugin; machine-learning-based classification of code snippets using a feature-engineered pipeline; the comparison of classical machine-learning models (SVM, Random Forest, XGBoost) and supplementary deep-learning models (LSTM, CodeBERT) under a shared evaluation protocol; the selection and production integration of XGBoost as the classification model; SHAP-based explainability for the production model; a Hybrid Decision Engine that combines model predictions with deterministic evidence; extraction of APK manifest metadata, including declared permissions, minimum and target SDK versions, and requested hardware features; compatibility analysis based on this verified, extracted metadata; a Flutter-based end-user application offering application search, security assessment, compatibility checking, alternative application ranking, and a security-oriented chatbot; persistence of application, scan, and user data in a MySQL database; and integration with IntelliJ-based IDEs, including Android Studio, for real-time and project-wide developer scanning.

The following are explicitly outside the scope of this research. The system is not designed as a complete Android malware detection solution and does not attempt to detect malicious behaviour beyond the two targeted vulnerability categories. It does not attempt to cover the full range of Common Weakness Enumeration (CWE) categories relevant to Android security, only CWE-89 and CWE-295. The system does not perform full binary reverse engineering of compiled application code; its APK-level analysis is limited to manifest metadata extraction and the static findings produced by the existing scanning pipeline. The system does not, and cannot, guarantee zero false negatives; its Decision Engine explicitly defers uncertain cases to manual review rather than forcing an automatic verdict, and its coverage and error rates are measured and reported rather than assumed to be perfect. Where trusted device or application metadata is not available, for example a device's RAM or CPU model, the system does not attempt to infer or guess this information, and reports it honestly as unavailable rather than fabricating a compatibility judgement. LSTM and CodeBERT are evaluated only as research comparison models in this work and are not integrated into the production detection pipeline. Finally, this research does not claim to provide a universal security certification for Android applications; its assessments are scoped to the evidence the system has actually gathered for a given code sample or application version.

## 1.7 Significance of the Research

**A. Significance for software developers.** DualVulnDroid provides developers with early, real-time detection of CWE-89 and CWE-295 as code is written, rather than requiring a separate, manually triggered scanning step. Findings are accompanied by source-to-sink data-flow evidence and SHAP-based explanation, allowing a developer to understand why a piece of code was flagged rather than receiving an unexplained warning. Where a finding matches a verified, safe remediation pattern, the plugin offers a Quick Fix that is scoped narrowly to the specific vulnerable expression, together with a re-scan to confirm that the fix genuinely resolved the finding, reducing both the effort and the risk associated with manual remediation.

**B. Significance for application users.** For a person deciding whether to install or continue using an Android application, DualVulnDroid's Flutter application provides an accessible security assessment expressed in plain language, together with a clear recommendation, an explanation of why a given risk level was assigned, and honest reporting of device compatibility based on verified manifest metadata. Where an application is assessed as high risk, the system can suggest alternative applications in the same category that have received a more favourable assessment, and a security-focused chatbot allows the user to ask follow-up questions about a specific application or about the underlying vulnerability categories.

**C. Significance for security researchers.** This research provides an evaluation of both classical machine-learning and deep-learning approaches to Android vulnerability detection across two distinct CWE categories under a shared, controlled evaluation protocol, including a comparison of overall and per-vulnerability-type false negative and false positive rates. It also contributes an analysis of a Hybrid Decision Engine's coverage, that is, the proportion of cases it is willing to decide automatically, against the reliability of those automatic decisions, together with a robustness study examining the stability of a candidate set of thresholds across alternative data splits.

**D. Significance for software engineering practice.** More broadly, this research illustrates one approach to integrating automated security analysis into the software development lifecycle in a way that keeps the machine-learning prediction and the evidence-based security decision as separate, clearly attributed components rather than a single opaque verdict. The resulting architecture, comprising a shared feature and detection pipeline, a decision layer, and separate developer- and user-facing interfaces, is intended to be a reusable pattern for future work extending detection to additional vulnerability categories or platforms, rather than a claim that Android application security in general has been solved.

## 1.8 Thesis Structure

The remainder of this thesis is organised into eleven further chapters.

**Chapter 2 — Literature Review** examines prior work on Android application security, static and data-flow analysis, machine-learning and deep-learning approaches to source-code vulnerability detection, and explainability techniques in security-focused machine learning, in order to position the contribution of this research relative to existing approaches.

**Chapter 3 — Methodology** describes the overall research methodology, from the preparation and cleaning of the labelled dataset through feature engineering, model training and comparison, decision-engine design, and the approach taken to production integration and end-to-end validation.

**Chapter 4 — System Design and Architecture** presents the architecture of DualVulnDroid, including the real-time and project-wide code analysis pipeline, the APK assessment pipeline, the database design, and the way the developer plugin, backend, and end-user application interact.

**Chapter 5 — Dataset and Feature Engineering** provides a detailed account of the dataset used for model training and evaluation, the process used to identify and exclude conflicting labels, and the design of the feature pipeline, including the deterministic security and data-flow features.

**Chapter 6 — ML/DL Model Development and Evaluation** presents the training configuration and evaluation results for the SVM, Random Forest, and XGBoost models, together with the supplementary LSTM and CodeBERT comparisons, including overall and CWE-specific performance.

**Chapter 7 — Hybrid Decision Engine and Explainability** describes the design of the Decision Engine that combines the production model's prediction with static and data-flow evidence, the SHAP-based explainability integrated into the production pipeline, and the coverage and robustness analysis conducted on the Decision Engine's thresholds.

**Chapter 8 — Software Implementation** describes the implementation of the IntelliJ developer plugin, the FastAPI backend, the MySQL database, and the Flutter end-user application, including the chatbot and its integration with real backend data.

**Chapter 9 — Testing and Validation** reports the automated and live-environment testing performed on the system, including backend, plugin, and Flutter test suites, headless IntelliJ Platform integration testing, and live validation on a real Android emulator.

**Chapter 10 — Results and Discussion** brings together the model comparison, Decision Engine, and system validation results to answer the research questions stated in this chapter, and discusses the resulting production model decision.

**Chapter 11 — Limitations and Future Work** discusses the limitations of the dataset, the evaluated models, the Decision Engine, and the extent of live-environment validation performed, and proposes directions for future work.

**Chapter 12 — Conclusion** summarises the contribution of the research, restates the final production model decision and its justification, and offers closing remarks on the outcome of the study.
