DUAL-VULNERABILITY DETECTION IN ANDROID CODE: REAL-TIME SQL INJECTION AND CERTIFICATE VALIDATION DETECTION
CHAPTER 02 – CRITICAL LITERATURE REVIEW AND RESEARCH GAP

## 2.1 Chapter Overview

This chapter critically reviews prior research relevant to DualVulnDroid, a real-time Android source-code vulnerability detection system targeting SQL Injection (CWE-89) and Improper Certificate Validation (CWE-295). The review examines Android application security and static analysis; SQL Injection and certificate-validation detection specifically; static, data-flow, machine-learning, deep-learning, and transformer-based detection techniques; explainable AI for security; and, centrally, real-time IDE-integrated security tooling. Rather than summarising papers individually, the chapter synthesises the literature by theme, comparing detection technique, Android relevance, evaluation approach, explainability, and developer-workflow integration across studies, in order to build an evidence-based argument toward the specific research gap DualVulnDroid addresses.

## 2.2 Literature Search and Selection Strategy

Relevant literature was identified through targeted searches of IEEE Xplore, the ACM Digital Library, Springer Link, ScienceDirect, USENIX, and Google Scholar (used for discovery only, not as a primary source), using search terms including "Android vulnerability detection," "Android static analysis security," "Android SQL injection detection," "CWE-89 Android," "CWE-295 certificate validation Android," "machine learning source code vulnerability detection," "deep learning vulnerability detection," "CodeBERT vulnerability detection," "IDE integrated security analysis," "real-time static analysis IDE," "explainable vulnerability detection," and "SHAP software vulnerability detection." arXiv preprints were included only where the work is directly relevant and is explicitly identified below as a preprint rather than a peer-reviewed publication.

This is a critical, thematically organised literature review conducted to support this thesis; it does not follow a formal, pre-registered systematic-review protocol (e.g., PRISMA), and is not presented as a systematic literature review. Studies were included where they addressed Android application security, source-code-level vulnerability detection (particularly CWE-89 or CWE-295), static or data-flow analysis techniques applicable to code, machine-learning or deep-learning approaches to vulnerability classification, explainability in security contexts, or IDE-integrated developer security tooling. Studies were excluded where they addressed only network-level or infrastructure-level attacks with no source-code detection component, or where their existence or reported details could not be independently verified against a publisher, DBLP, or arXiv record. Recent studies (approximately 2020–2026) were prioritised for current ML/DL and IDE-integration techniques, while seminal earlier work (e.g., foundational SQL Injection classification, taint analysis, and Android SSL studies from the 2005–2015 period) is retained where it remains the primary source for a concept still relied upon.

## 2.3 Android Application Security and Vulnerability Detection

Android application security research has long distinguished between manual code review, which does not scale to the volume of code produced in modern development and is inconsistent across reviewers, and automated static analysis, which can process large codebases but must trade completeness against computational cost and false-positive rate. Foundational static and taint-analysis tools for Android, notably FlowDroid (Arzt et al., 2014) and the dynamic tracker TaintDroid (Enck et al., 2010), established that a value's propagation from an untrusted source to a security-sensitive sink can be modelled and checked automatically, providing a form of evidence manual review cannot reliably produce at scale. However, both tools evaluate a narrow, technique-specific question, information-flow leakage, rather than classifying arbitrary code as vulnerable or safe across multiple weakness categories, and neither integrates its findings into a real-time, in-editor developer workflow. This establishes the underlying motivation, evidenced directly in the reviewed literature, for automated, source-code-level vulnerability detection: existing static/taint techniques provide genuine, verifiable evidence but are narrow in scope and are not, on their own, packaged for continuous developer use, a limitation returned to in Section 2.11.

## 2.4 SQL Injection Detection — CWE-89

Research on SQL Injection detection can be broadly grouped into pattern/rule-based static detection, taint/data-flow analysis, and, more recently, machine-learning and deep-learning classification, and the reviewed studies differ considerably in dataset design and in whether Android is evaluated specifically rather than web applications generally. Halfond, Viegas and Orso's early classification of SQL Injection attack types and countermeasures established that no single detection or prevention technique covers the full scope of the problem, a conclusion still reflected in the diversity of approaches reviewed here. Livshits and Lam demonstrated that static, points-to-based analysis translating user-specified vulnerability signatures into automated checkers can detect Java injection-style vulnerabilities with reasonable precision, but such an approach depends on manually authored signatures and is not Android-specific.

More recent work has combined data-flow reasoning with symbolic or concolic execution to reduce the false positives inherent in purely syntactic pattern matching: ConsiDroid (Ermuth et al., 2018, arXiv preprint) uses concolic execution guided by static analysis to inspect only suspicious execution paths for Android SQL Injection, evaluated on a small sample of real-world F-Droid applications. This illustrates a recurring trade-off in the SQL Injection literature: static/data-flow approaches provide explicit, checkable reasoning about how a query is constructed, but this reasoning is comparatively expensive to compute and does not generalise to a vulnerable pattern the analysis was not designed to recognise, whereas machine-learning approaches, reviewed further in Section 2.7, can in principle learn a broader family of patterns from labelled examples but depend on the size and representativeness of that labelled data, and typically classify a code sample without producing an explicit source-to-sink trace of their own.

Directly Android-specific, ML-based CWE classification is provided by the Senanayake et al. (2022, 2023c) programme of work built on the LVDAndro dataset, discussed in full in Section 2.11–2.12, which includes SQL Injection among the CWE categories its ensemble classifier targets and reports strong aggregate accuracy on Android source code; however, the published descriptions of this work do not report a dedicated evaluation isolating SQL Injection detection performance or false-negative rate specifically, nor a description of an explicit source-to-sink evidentiary trace comparable to FlowDroid's, a gap this review treats as "not reported" rather than assumed absent. Taken together, the SQL Injection literature reviewed here supports the position that static/data-flow evidence and learned classification address different, complementary aspects of the detection problem, motivating DualVulnDroid's decision (detailed in Chapter 3) to combine both rather than rely on either alone.

## 2.5 Certificate Validation Vulnerabilities — CWE-295

Empirical studies of Android TLS/SSL usage established, independently of any single detection tool, that certificate and hostname validation is a genuinely widespread, practically exploitable weakness rather than a theoretical concern: Fahl et al.'s large-scale analysis of 13,500 Android applications found a meaningful proportion contained SSL/TLS code potentially vulnerable to man-in-the-middle attacks, with manual testing confirming exploitability in a subset of examined apps, and Georgiev et al. showed the same class of failure recurring across non-browser software more broadly, attributing much of it to confusing SSL/TLS API design rather than isolated developer error.

Detection approaches specifically for this vulnerability class fall into static API-pattern detection and combined static/dynamic verification. SSLINT (He et al., 2015) performs scalable static analysis against signatures of correct SSL/TLS API use to flag incorrect hostname/certificate validation, identifying previously unknown vulnerabilities in real deployed software. DCDroid (Wang et al., 2020) extends this specifically to Android, combining static identification of vulnerable schema with dynamic UI-driven confirmation, and reporting that a substantial proportion of a large sample of real Android apps contained potentially vulnerable SSL/TLS code, with a smaller but still substantial proportion confirmed exploitable after dynamic verification. Across this literature, a consistent method is used to identify the vulnerable pattern: a HostnameVerifier or TrustManager implementation whose body unconditionally accepts a certificate or hostname rather than delegating to the platform's real validation logic. This pattern-based approach benefits from a well-defined, precisely describable vulnerable shape, but the reviewed static tools generally confirm findings through separate dynamic analysis (as in DCDroid) precisely because a purely static signature match cannot, on its own, distinguish a genuinely reachable, exploitable configuration from an unreachable or already-mitigated one.

A recurring observation across the reviewed certificate-validation literature is that it is treated as a standalone security-configuration problem, evaluated with its own dedicated tools (SSLINT, DCDroid) and its own dedicated empirical studies, rather than being combined with other vulnerability categories such as SQL Injection within one detection workflow; none of the certificate-validation-specific studies reviewed here also evaluate SQL Injection detection, and none of the SQL-Injection-specific studies reviewed in Section 2.4 also evaluate certificate validation. Machine-learning-based detection specifically for CWE-295 is comparatively sparse in the reviewed literature; the Senanayake et al. (2022, 2023c) CWE-based classifier again includes certificate/cryptographic-related CWE categories within its broader label set, but, as with SQL Injection above, no dedicated, isolated evaluation of certificate-validation detection performance was found in the available published descriptions. This absence of a unified, dual-vulnerability treatment across the reviewed literature is used in Section 2.15 to support the vulnerability-coverage research gap.

## 2.6 Static Analysis and Data-Flow-Based Vulnerability Detection

Across both vulnerability categories, the static and data-flow analysis literature reviewed above (Livshits & Lam; Arzt et al.; He et al.; Wang et al.) consistently demonstrates a genuine strength: an explicit, checkable account of how a value moves from a source to a sink, or of exactly which API call pattern is present, that does not depend on a trained model's internal parameters. Its consistently reported limitation is scalability and rule-maintenance cost: FlowDroid's own motivation is that earlier, coarser Android taint approaches produced high false-negative and false-positive rates before more precise, but more expensive, context- and lifecycle-aware modelling was introduced, and SSLINT/DCDroid both require maintained, hand-specified signatures of correct API usage. This literature is used in DualVulnDroid's architecture not as a technique to be replaced, but as one of two evidence sources feeding a Hybrid Decision Engine, described fully in Chapter 3: static and data-flow evidence, of the kind established as valuable but narrow above, is combined with the machine-learning prediction reviewed next, on the basis that the two sources have complementary, not overlapping, weaknesses. This combination is described here as the specific design decision it is, not as a claim that static analysis itself is a novel contribution of this research.

## 2.7 Machine Learning for Source-Code Vulnerability Detection

Classical machine-learning approaches transform code into a feature vector, typically combining lexical features such as TF-IDF-weighted token or character n-grams with, in security-specific work, handcrafted indicators of known-risky patterns, and train a supervised classifier such as a Support Vector Machine (Cortes & Vapnik, 1995), Random Forest (Breiman, 2001), or a gradient-boosted tree ensemble such as XGBoost (Chen & Guestrin, 2016) to distinguish vulnerable from safe examples. Compared with static analysis, these approaches can in principle generalise beyond an explicitly authored rule, learning statistical regularities in how vulnerable code tends to be written; compared with deep learning, reviewed next, they are markedly cheaper to train, require less labelled data to reach a stable result, and, in the case of tree-based ensembles particularly, support post-hoc feature-attribution explanation (Section 2.10) more directly than an opaque neural sequence model. Their reported limitation, consistent across the classical-ML studies reviewed here and in the broader vulnerability-detection literature, is a strong dependence on the specific feature representation and on the size and diversity of labelled training data; a purely lexical representation cannot itself encode a source-to-sink relationship unless a dedicated feature is engineered to capture it. Because no single classical algorithm is shown in the reviewed literature to dominate across datasets, feature representations, and vulnerability types, DualVulnDroid's research design (detailed in Chapter 3) evaluates multiple classical models (SVM, Random Forest, XGBoost) under an identical protocol rather than assuming in advance that one is universally superior.

## 2.8 Deep Learning for Vulnerability Detection

Sequence- and graph-based deep-learning approaches extend the classical paradigm by learning a representation of code directly rather than relying on hand-designed features. Devign (Zhou et al., 2019) represents code as a composite graph combining abstract syntax, control-flow, and data-flow information and reports improved detection accuracy over prior learning-based methods on its evaluation set; IVDetect (Li, Wang & Nguyen, 2021) similarly uses graph-based representations while explicitly targeting fine-grained, statement-level interpretability of its own predictions, addressing the explainability gap discussed in Section 2.10. Sequence models such as LSTMs have also been widely applied to tokenised code. A pointed, directly relevant critical finding comes from Chakraborty, Krishna, Ding and Ray's empirical study of deep-learning-based vulnerability detection, which found that several published DL detectors, when evaluated on more realistic, less curated real-world data than their original benchmarks, suffered a performance drop of more than 50%, indicating that strong benchmark performance does not reliably transfer to real-world deployment conditions. This literature therefore motivates evaluating deep learning empirically rather than assuming its architectural sophistication translates into superior real-world performance; DualVulnDroid's own LSTM evaluation, reported as an empirical result in Chapter 6, is designed and interpreted in light of this documented literature-wide caution, not as a foregone conclusion that a from-scratch sequence model would outperform the classical baselines reviewed in Section 2.7.

## 2.9 Transformer-Based Code Models and CodeBERT

Transformer-based pretrained code models represent a further extension: rather than learning a task-specific representation from a single labelled dataset, a Transformer encoder is first pretrained on a very large corpus of code (and, for bimodal models, paired natural-language text), producing contextual representations that can then be fine-tuned on a smaller, task-specific dataset. CodeBERT (Feng et al., 2020) is a bimodal Transformer pretrained jointly on natural-language/programming-language pairs across six languages, intended to support downstream code-understanding tasks including, but not limited to, vulnerability-related classification. GraphCodeBERT (Guo et al., 2021) extends this by pretraining on data-flow information rather than treating code purely as a token sequence, explicitly incorporating a semantic-level "where-the-value-comes-from" relationship between variables into the pretraining objective, directly relevant to source-to-sink reasoning. VulBERTa (Hanif & Maffeis, 2022) demonstrates that a comparatively simple RoBERTa-style pretraining pipeline, applied specifically to open-source C/C++ code, can achieve strong vulnerability-detection performance across several established benchmarks despite its conceptual simplicity and comparatively modest training-data and parameter requirements relative to larger contemporary models.

This literature establishes a genuine, theoretically grounded advantage for pretrained Transformer models: general code knowledge acquired during large-scale pretraining can reduce the amount of task-specific labelled data needed to reach strong performance, compared with a model trained entirely from scratch. It also establishes real costs and constraints, again consistent across the studies above: fine-tuning a Transformer of this kind requires materially more computation than the classical models in Section 2.7, and the advantage from pretraining does not remove the dependence on a sufficiently representative fine-tuning dataset for the specific target task, particularly on a small, domain-specific dataset such as an Android-focused CWE-89/CWE-295 corpus. This motivates CodeBERT's role in this research as a research-only comparative model, fine-tuned and evaluated under the same protocol as the classical models: its numerical results are an empirical finding of this thesis (reported in Chapter 6), not assumed in advance from the literature reviewed here, which establishes only the theoretical basis for expecting it to be a strong, but not automatically superior, candidate.

## 2.10 Explainable AI for Security/Vulnerability Detection

A security classifier that returns only a bare "vulnerable" or "safe" label provides little basis for a developer to trust, verify, or act on that verdict. SHAP (Lundberg & Lee, 2017) addresses this by assigning each input feature a signed contribution to a specific prediction within a theoretically grounded, unified feature-attribution framework, and has been applied specifically within security contexts, including vulnerability-detection debugging and explanation workflows reported in the reviewed 2021–2023 literature. IVDetect (Li, Wang & Nguyen, 2021) similarly targets fine-grained, statement-level interpretation directly within a graph-based vulnerability detector, rather than adding attribution as a separate, post-hoc step. Across this literature, explanation is consistently framed as supporting developer understanding, debugging, remediation prioritisation, and the manual-review process specifically for the cases a system does not resolve automatically, rather than as a substitute for detection performance itself.

It is important not to overstate what SHAP or comparable attribution methods actually guarantee: the reviewed literature is explicit that such methods explain a model's own learned behaviour, which features it weighted most heavily for a given prediction, and do not themselves constitute an independently verified account of the underlying code's real security properties; one study noted the additional computational cost of adding SHAP explanations at scale as a practical deployment consideration. DualVulnDroid's implemented explanation mechanism, described in Chapter 3, is directly grounded in this literature: SHAP is applied to the production XGBoost model specifically as a model-level explanation, kept explicitly distinct from the separate, deterministic static/data-flow evidence discussed in Section 2.6, rather than the two being merged into one undifferentiated "explanation" output.

## 2.11 Real-Time IDE / Plugin-Based Security Analysis

This is the most directly relevant theme to DualVulnDroid's core contribution, and the literature here draws a clear distinction between a security detection model, evaluated offline against a held-out dataset, and a complete developer-integrated workflow that surfaces findings inside the editor as code is written. Commercial IDE security plugins (e.g., vendor-supplied SAST/SCA integrations for IntelliJ) demonstrate that real-time, in-editor feedback is achievable in practice, but published, independently verifiable technical detail on their underlying detection technique, Android-specific CWE coverage, or explainability mechanism is generally not available in the academic literature, and is accordingly treated here as "not reported" rather than assumed.

The most directly comparable published academic work is the Senanayake et al. programme: LVDAndro (Senanayake et al., 2023c) is a large, CWE-labelled Android source-code dataset built by scanning over 15,000 real applications and automatically labelling code samples using an existing vulnerability scanner; a related short paper (Senanayake et al., 2022) reports an ensemble machine-learning model trained on this style of data achieving strong reported F1-scores for both binary vulnerability detection and CWE-category classification; and ACVED (Senanayake et al., 2023a) is an open-source, AI-powered Android Studio plugin, built on the LVDAndro dataset, that reports providing developers with the vulnerability status of the current source-code line in real time and receiving ongoing dataset updates to cover newly added CWE categories. This is a genuine, real-time, ML-based, Android-specific, IDE-integrated vulnerability detection system, and its existence is treated in this review as important prior art rather than overlooked.

Evaluated against the ten criteria motivating this section, real-time source-code analysis, CWE-specific detection, Android-specific detection, ML-based detection, explainable predictions, developer-facing evidence, Quick Fix support, backend/API integration, hybrid ML plus static analysis, and detection of multiple vulnerability classes, the published descriptions of ACVED confirm the first four and the last (real-time, CWE-specific, Android-specific, ML-based, multiple CWE categories) directly. The available published material does not report an explicit, separately surfaced static/data-flow evidence trace comparable to Section 2.6, a model-level explanation mechanism comparable to SHAP, or an automated, safety-scoped Quick Fix remediation feature; these are recorded here as "not reported" in the available descriptions of that system, not as a claim that ACVED categorically lacks them. This comparison is used directly in Section 2.15 to motivate the integration and explainability gaps: even the closest identified prior work, a genuine real-time, ML-based, Android-CWE-aware IDE plugin, is not documented in the reviewed literature as also combining deterministic static/data-flow evidence, model-level explanation, and safety-scoped automated remediation within one Decision-Engine-style workflow, which is the specific combination DualVulnDroid implements.

## 2.14 Critical Synthesis

Six patterns recur across the literature reviewed above, each directly supported by the studies cited rather than asserted independently of them.

**Pattern 1 — static analysis provides strong, checkable reasoning but limited adaptability.** FlowDroid, TaintDroid, SSLINT, and DCDroid each provide an explicit, verifiable account of a specific vulnerable pattern or data flow, but each depends on a maintained model of the platform/API or a maintained signature set, and none is shown in the reviewed literature to generalise automatically to a pattern outside that model.

**Pattern 2 — ML approaches learn patterns but depend on data and representation.** The classical-ML and Android-specific-ML literature (Senanayake et al.) consistently reports strong aggregate performance, but the reviewed publications do not report isolated, per-CWE false-negative analysis for CWE-89 or CWE-295 specifically, and classical-ML performance throughout this literature is tied to the chosen feature representation.

**Pattern 3 — DL/Transformer models offer richer representations at higher cost, without a guaranteed accuracy advantage.** Devign, IVDetect, CodeBERT, GraphCodeBERT, and VulBERTa each demonstrate a genuine representational advantage over purely lexical features, yet Chakraborty et al.'s empirical study directly demonstrates that this architectural sophistication does not reliably translate into robust real-world performance, and no reviewed DL/Transformer study is shown to categorically outperform well-engineered classical baselines across settings.

**Pattern 4 — the literature more often reports model accuracy than developer-facing real-time integration.** Of the twenty studies compared in Table 2.2, real-time IDE integration is confirmed for only one, ACVED, indicating that offline evaluation remains the dominant reporting practice even where a technique could plausibly be integrated into a live workflow.

**Pattern 5 — explainability is not consistently integrated into vulnerability-detection workflows.** SHAP and IVDetect demonstrate that explanation is achievable, but of the twenty studies in Table 2.2, only these two report an explicit explainability mechanism, and ACVED's published description does not report one, indicating explainability remains an add-on in a minority of the reviewed systems rather than a standard component.

**Pattern 6 — CWE-89 and CWE-295 are consistently studied separately.** Every SQL-Injection-specific study reviewed in Section 2.4 and every certificate-validation-specific study reviewed in Section 2.5 evaluates its own vulnerability category alone; even the broader, multi-CWE Senanayake et al. line of work does not report an isolated, per-category evaluation distinguishing CWE-89 from CWE-295 performance.

## 2.15 Research Gap

The reviewed literature suggests five specific, evidence-based gaps rather than a claim that no comparable system exists. First, an **integration gap**: across the studies compared in Tables 2.1 and 2.2, detection models (classical ML, DL, Transformer) and static/data-flow tools are generally evaluated and published independently of one another, and even ACVED, the closest identified real-time Android IDE tool, does not report combining ML prediction with a separately surfaced static/data-flow evidence trace. Second, a **vulnerability coverage gap**: consistent with Pattern 6, CWE-89 and CWE-295 are not evaluated together within one unified, per-category-reported real-time detection workflow in any study reviewed here. Third, an **explainability gap**: consistent with Pattern 5, only a minority of the reviewed detection systems report an explicit explanation mechanism, and the one directly comparable real-time Android tool, ACVED, does not report one in its published description. Fourth, a **real-time developer workflow gap**: consistent with Pattern 4, the majority of ML/DL vulnerability-detection studies reviewed here (Devign, IVDetect, CodeBERT, GraphCodeBERT, VulBERTa) evaluate models offline against held-out datasets without demonstrating continuous, in-editor feedback, ACVED being the documented exception rather than the norm. Fifth, an **evaluation gap**: the reviewed ML/DL studies use different datasets, different label taxonomies, and different metrics (Devign's own accuracy/F1 versus VulBERTa's benchmark suite versus Senanayake et al.'s aggregate F1), which the evidence indicates makes direct, like-for-like comparison across studies difficult, motivating a controlled, single-protocol comparison as a specific methodological requirement rather than reliance on cross-paper figures. Across the studies examined, these five gaps are consistently, if not universally, present, and together motivate a system that evaluates multiple models under one protocol, combines ML prediction with static/data-flow evidence in an explicit decision process, reports model-level and evidence-level explanation separately, integrates detection into a real-time IDE workflow, and treats CWE-89 and CWE-295 as a joint, not isolated, evaluation target.

| No single ML/DL/Transformer family is shown to dominate across settings (Pattern 3; Sections 2.7–2.9). | Evaluate multiple ML/DL models (SVM, Random Forest, XGBoost, LSTM, CodeBERT) under one shared protocol. |
| Security predictions are difficult for developers to interpret without explicit attribution (Section 2.10). | Provide SHAP-based model explanation, kept explicitly distinct from static/data-flow evidence. |
| Most reviewed detection research evaluates offline, without demonstrated continuous developer feedback (Pattern 4; Section 2.11). | Integrate detection into a real-time IntelliJ/Android Studio plugin workflow. |
| CWE-89 and CWE-295 are consistently evaluated separately, including in the closest identified prior tool (Pattern 6; Section 2.15). | Evaluate and report both CWE-89 and CWE-295 within one unified pipeline and one set of reported metrics. |
| Chakraborty et al. show DL performance can drop sharply under real-world conditions; false negatives carry particular security consequence (Section 2.8). | Evaluate recall and false-negative rate explicitly, not only accuracy, and defer uncertain cases via a Decision Engine rather than forcing an automatic verdict. |
| Explainability is inconsistently integrated, and the closest real-time tool does not report one (Pattern 5; Section 2.11). | Surface both SHAP and static/data-flow evidence to the developer for every finding, not only high-confidence ones. |

## 2.17 Chapter Summary

The literature reviewed in this chapter establishes that static and data-flow analysis provide genuine, checkable evidence but do not adapt beyond their designed scope; that classical machine learning and, more recently, deep-learning and Transformer-based models can learn broader vulnerability patterns but remain dependent on data quality, representation, and, per Chakraborty et al.'s empirical finding, do not reliably generalise to real-world conditions without direct evaluation; that explainability techniques such as SHAP exist and are applicable to security classification but are inconsistently adopted; and that real-time, IDE-integrated, ML-based Android vulnerability detection is achievable in practice, as demonstrated by the closest identified prior system, ACVED, but is not documented in the reviewed literature as also combining static/data-flow evidence, separated model-level explanation, and joint CWE-89/CWE-295 treatment within one workflow. From this evidence, five specific gaps, integration, vulnerability coverage, explainability, real-time developer workflow, and evaluation consistency, were identified directly from the comparative analysis in Sections 2.12–2.14, and translated into concrete design requirements in Section 2.16. These requirements, a shared multi-model evaluation protocol, combined ML and static/data-flow evidence, separated explanation, real-time IDE integration, and joint dual-CWE coverage with explicit false-negative reporting, define the methodological problem addressed in Chapter 3, which describes how DualVulnDroid's dataset, feature engineering, model comparison, and Decision Engine were actually designed and evaluated to meet them.
