## 6.4 Backend Implementation

`app.py` is implemented as a single FastAPI application with Pydantic request models (`CodeRequest`, `BatchScanRequest`, `ChatMessage`, `DeviceProfile`, and others) validating every request body before a route handler runs. Route handlers are deliberately thin: they perform request-shape decisions (e.g. `_guarded_predict()`'s 200KB size guard) and call into the shared analysis core or data-access layer, rather than embedding analysis logic inline. Startup wires a best-effort database connectivity check (`_startup_database_check()`, calling `check_connection()` from `db/session.py`) that logs a warning rather than blocking startup, since routes such as `/predict` have no database dependency. Three exception handlers are registered at the application level — a generic `Exception` handler, an `HTTPException` handler, and a `DatabaseNotConfiguredError` handler — so every route inherits the same error-response shape without repeating the same `try`/`except` in each handler.

The end-to-end request flow implemented for a vulnerability-analysis request is: **Input → API → feature construction → XGBoost → probability/confidence → SHAP → security/data-flow evidence → Decision Engine → response**, realised concretely as follows.

`predict_code(code, file_name)` in `predictor.py` is the single function that implements this whole sequence and is called by every route that needs an analysis result (`/predict`, `/developer/predict`, `/developer/scan`, `/developer/explain`, `/developer/rescan`, `/decision`). It begins with a guard clause returning an early `SAFE`/`none` response for empty input, then branches: files ending in `.xml` are handled by a small, separate rule-based engine that inspects `AndroidManifest.xml` for `android:usesCleartextTraffic="true"` and `network_security_config.xml` for permissive `<base-config>`/`<certificates src="user">` entries outside a `<debug-overrides>` block — this branch does not use the ML pipeline at all, since these are structural manifest/configuration facts rather than code patterns. For Java/Kotlin source, the function proceeds through feature construction, XGBoost prediction, SHAP explanation, rule/data-flow evidence extraction, and Decision Engine evaluation, returning one dictionary consumed identically by every calling route.

## 6.5 Security Feature Extraction Implementation

`security_features.py` implements `extract_security_features(code)`, which converts the output of `dataflow.py`'s analyzers plus a small set of direct structural checks into the fixed-order, 23-element `FEATURE_NAMES` vector already documented architecturally in Chapter 5. The implementation is a pure function of the code text — no randomness, no external state — which is a deliberate implementation property: it guarantees the same snippet always produces the same feature vector, which is required for the training/inference parity that `ml/feature_pipeline.py` depends on when it imports this exact module for both purposes.

Concretely, the function calls `analyze_sql_dataflow(code)`, `analyze_cert_dataflow(code)`, and `sql_sink_safety_summary(code)` (all from `dataflow.py`) once, then derives each of the 23 features from their output plus a handful of direct substring/regex checks on the lower-cased code — for example, `sql_raw_query` is `int(".rawquery(" in lower)`, while `sql_source_to_sink` is derived from whether any `dataflow.py` finding has `detection_basis` equal to `"traced-source"` or `"traced-source-interprocedural"`. `dataflow.py` itself implements a deliberately scoped static analyzer: single-file, statement-per-line analysis with intraprocedural taint tracking through variable assignment and string concatenation, plus exactly one bounded interprocedural hop (a tainted value passed as an argument into another method defined in the same file). Certificate-validation checks are structural — the analyzer inspects the actual body of `HostnameVerifier`/`X509TrustManager`/`onReceivedSslError` implementations rather than performing a whole-file keyword search, so that a custom implementation which genuinely validates is not blanket-flagged.

`extract_security_feature_vector(code)` wraps this into a plain ordered list, ready to be concatenated with the TF-IDF/count matrices in `ml/feature_pipeline.py`.

## 6.6 XGBoost Production Model Implementation

**Production model:** XGBoost. **Feature dimension:** 7,610. **Selected rounds:** 103 of 123.

`predictor.py` loads the production model from `research_eval_artifacts/xgboost/` — specifically `model.json` and `metadata.json` — rather than from the older `ml/artifacts/` directory, which is kept on disk only for historical reference and is no longer loaded. This artefact is the exact model whose test-set performance was the basis for selecting XGBoost as the production model in the research comparison reported in earlier chapters. The loader reads `metadata.json`'s `final_hyperparameters.num_boost_round_selected` value, loads the raw booster with `xgb.Booster().load_model(MODEL_PATH)`, and then slices it — `model = _raw_booster[0:_NUM_BOOST_ROUND_SELECTED]` — before it is ever used for prediction. This slicing exists because the saved booster contains more trees than were actually selected: early stopping trains a fixed number of extra rounds past the best iteration before halting, so predicting with the raw, unsliced booster would silently use additional, non-selected trees and would not reproduce the evaluated research result. The slice is applied once, at load time, so every later call to `model.predict()` and the `shap.TreeExplainer` built against `model` automatically only ever see the validated 103 rounds — no call site elsewhere in the codebase needs to remember an iteration range.

The model is versioned by content hash: `PRODUCTION_MODEL_INFO` records a 12-character SHA-256 prefix of the loaded `model.json` file (`modelVersion`) and of the loaded word-vectorizer artefact (`featurePipelineVersion`), alongside `classOrder` and `numBoostRoundSelected`, so a caller can always determine at runtime exactly which trained artefact is being served.

**Class order:** the production label mapping (`LABELS_ORDER` in `ml/evaluate.py`, reused by `predictor.py`'s `reverse_mapping`) is `["s0", "v0", "s1", "v1"]` — that is, `s0=0`, `v0=1`, `s1=2`, `v1=3`. `LABEL_INFO` in `predictor.py` maps these directly to vulnerability status and type: `s0` is SQL-Injection-vulnerable, `s1` is SQL-Injection-safe, `v0` is Certificate-Validation-vulnerable, `v1` is Certificate-Validation-safe. This mapping is not re-derived anywhere else in the system; every downstream consumer (the Decision Engine's `VULNERABLE_ML_LABELS = {"s0", "v0"}`, the plugin's response parsing, the Flutter client) relies on this same fixed ordering.

This chapter does not describe LSTM or CodeBERT as production components, because neither is loaded or called anywhere in `predictor.py` or any route in `app.py`. **Production: XGBoost. Research comparison: Linear SVM, Random Forest, XGBoost, LSTM, CodeBERT** — the latter four (including XGBoost itself, evaluated a second time under identical fair-comparison conditions) were assessed during the research phase reported in earlier chapters; only XGBoost was carried forward into `predictor.py`.

## 6.7 Machine Learning Prediction Pipeline

**Figure 6.2. XGBoost Feature-to-Prediction Flow.** *(figure_6_2_xgboost_feature_to_prediction.png)*

`ml/feature_pipeline.py` implements the single, shared feature-construction path used by both training (`ml/train.py`, `ml/dataset_prep.py`, and the `research_eval/` training scripts) and live inference (`predictor.py`) — the module's own docstring states this exists specifically so training and inference cannot drift apart. `normalize_code()` lower-cases the text, strips `//` and `/* */` comments, masks string and character literals (`"..."` → `STRING`, `'...'` → `CHAR`) and numeric literals (→ `NUMBER`), and collapses whitespace, before the normalised text is passed to three separately-fitted scikit-learn vectorisers: a word-level `TfidfVectorizer` (`max_features=5000`, n-grams 1–3), a character-level `TfidfVectorizer` (`max_features=2000`, n-grams 2–5), and a `CountVectorizer` (`max_features=1000`, n-grams 1–2). `build_feature_matrix()` transforms the normalised code through all three fitted vectorisers, calls `extract_security_feature_vector()` for the 23 security features, and concatenates all four parts with `scipy.sparse.hstack()` into the final feature matrix passed to XGBoost as an `xgb.DMatrix`. All three vectorisers were fit exclusively on the training split and are loaded at backend startup from pre-fitted `joblib` artefacts (`research_eval_artifacts/shared_features/`), never re-fit at inference time.

`predict_code()` calls `model.predict(dmatrix)` to obtain a four-element probability array, then `np.argmax()`/`np.max()` to obtain the predicted label index and its confidence, before proceeding to SHAP and Decision Engine evaluation.

## 6.8 SHAP Explainability Implementation

**Figure 6.3. SHAP + Decision Engine Implementation Flow.** *(figure_6_3_shap_decision_engine_flow.png)*

`shap.TreeExplainer(model)` is instantiated exactly once, at module import time in `predictor.py`, against the same sliced, 103-round production booster used for prediction — this is an explicit implementation property, not incidental: because the explainer is built from the identical `model` object the backend serves, every SHAP value computed against it corresponds to the actual production booster, not to a separately-trained or differently-configured explainer. If explainer construction fails (caught in a `try`/`except` around the instantiation), `explainer` is set to `None` and `ALL_FEATURE_NAMES` to an empty list, and the rest of `predict_code()` degrades gracefully — SHAP-dependent fields are simply omitted rather than the request failing.

For each prediction, `explainer.shap_values(dmatrix)` is called twice within `predict_code()`: once to build `shapTopFeatures` (the top 8 features by absolute SHAP value for the predicted class, used by developer-facing explanations), and once inside a per-class loop that considers every class with predicted probability above 5%, extracting the top 10 positive-contribution features for line-matching against the actual source text (Section 6.13). The implementation handles three different SHAP output shapes defensively (a list of per-class arrays, a 3-dimensional array, or a single 2-dimensional array), reflecting real differences across SHAP library versions rather than an assumption about a single fixed output shape.

SHAP values are used here strictly as feature attribution — a measure of how much each feature pushed the model's output toward or away from a given class for this specific input — and the implementation does not claim or rely on SHAP values as proof of a causal relationship between a feature and the underlying vulnerability; they inform, alongside independently-computed data-flow evidence, what the Decision Engine and the developer-facing explanation surface.

## 6.9 Hybrid Decision Engine Implementation

`decision_engine.py` implements the Decision Engine as three functions: `compute_evidence()`, `decide()`, and `evaluate()` (which composes the first two). `compute_evidence()` takes the predicted label, its confidence percentage, the SQL and certificate data-flow findings, the parameterised-sink safety summary, and a boolean for whether a static keyword rule also matched, and returns a signed `evidence_score` plus a list of `reasons`, each recording its source, a human-readable detail, and its numeric contribution. The ML prediction itself contributes `±ml_confidence × ML_WEIGHT (1.0)`, signed positive when the predicted label is in `VULNERABLE_ML_LABELS = {"s0", "v0"}` and negative otherwise; the remaining weights (traced source-to-sink `+2.0`, unparameterised concatenation `+1.2`, confirmed parameterised query `−1.5`, certificate vulnerable `+2.0`, certificate suspicious `+0.6`, certificate safe `−1.5`, static-rule corroboration `+0.4`) are added by inspecting the real `sql_flow`/`cert_flow`/`sink_safety` structures passed in — none of these weights are re-derived per request; they are the fixed module-level constants documented in the file's own header comment.

`decide(evidence_score, vulnerable_threshold, safe_threshold)` implements the three-way comparison: `evidence_score >= vulnerable_threshold` → `"VULNERABLE"`; `evidence_score <= safe_threshold` → `"SAFE"`; otherwise → `"SUSPICIOUS_REVIEW"`. The thresholds passed to `decide()` are **not** the module's hand-picked reference defaults (`VULNERABLE_THRESHOLD = 1.5`, `SAFE_THRESHOLD = -0.9`) unless no calibration artefact exists; on import, the module checks for `ml/artifacts/decision_engine_thresholds.json` (produced by `ml/calibrate_decision_engine.py` from the validation split, never the test split) and, when present, overwrites both constants with the calibrated pair before any request is served. This chapter documents the production behaviour: the thresholds actually applied are the calibrated values loaded from that JSON artefact, not the reference defaults, and this chapter has made no change to either the reference defaults or the calibration artefact.

`SUSPICIOUS_REVIEW` exists as a deliberate third state rather than an implementation gap: the module's own documentation records that mapping it to `vulnerable=True` was considered and rejected, because at the coverage level this decision boundary produces (approximately 35% of cases auto-decided as clearly `VULNERABLE`/`SAFE`), doing so would place a warning on most scanned files — including plainly unrelated code — since neither the plugin nor the Flutter app has a dedicated "needs review" UI. `evaluate()`'s full three-way `decision` value is still always returned, so a future review-queue UI could distinguish "confidently safe" from "uncertain, ask a human" without any schema change; only the boolean `vulnerable` field collapses `SAFE` and `SUSPICIOUS_REVIEW` together, for backward compatibility with clients that only understand a boolean flag.

## 6.10 CWE-89 SQL Injection Detection Implementation

CWE-89 detection is not one function but the composition of several already-described implementation pieces, applied specifically to the `s0`/`s1` classes and to SQL-specific evidence. **Detection signals:** `dataflow.py`'s `analyze_sql_dataflow()` performs the intraprocedural (plus one-hop interprocedural) taint tracking from a defined set of `SQL_SOURCES` (e.g. `Intent.getStringExtra`, `EditText.getText`) to `SQL_SINK_NAMES` (e.g. `rawQuery`, `execSQL`), classifying each finding's `detection_basis` as `traced-source`, `traced-source-interprocedural`, or `unparameterized-concatenation`; `sql_sink_safety_summary()` separately reports whether every SQL sink call in the file uses parameterised placeholders. **Relevant security features:** `sql_source_detected`, `sql_sink_detected`, `sql_source_to_sink`, `sql_string_concatenation`, `sql_parameterized_query`, `sql_user_input`, `sql_raw_query`, `sql_exec_sql`, `sql_compile_statement` (9 of the 23 features in `security_features.py`). **ML classification:** the `s0`/`s1` probability pair from the same 4-class XGBoost softmax described in Section 6.6. **Supporting evidence:** the Decision Engine weights traced source-to-sink at `+2.0`, unparameterised concatenation at `+1.2`, and confirmed parameterisation at `−1.5`, independently of the model's own `s0`/`s1` probability. **Explanation/remediation:** `generate_explanation_sentences()` in `predictor.py` builds developer-facing sentences purely from already-computed real values (e.g. "User-controlled input reaches SQL execution." only when `sql_source_to_sink` is actually set), and `chatbot_logic.py`'s fixed `CWE_89_EXPLANATION` text describes the standard fix (parameterised queries with `?` placeholders) for conversational questions.

This detection path does not claim perfect coverage: `dataflow.py`'s own documentation states it is a deliberately scoped, single-file, statement-per-line analyzer, not a full whole-program static analyzer, and the ML component's own confidence is one signed input among several rather than a guaranteed-correct verdict.

## 6.11 CWE-295 Certificate Validation Detection Implementation

CWE-295 detection follows the same compositional pattern, applied to the `v0`/`v1` classes and to certificate-specific evidence. **Detection signals:** `dataflow.py`'s `analyze_cert_dataflow()` inspects the actual body of `HostnameVerifier.verify()`, `X509TrustManager.checkServerTrusted()`/`checkClientTrusted()`, and WebView `onReceivedSslError()` implementations, assigning each a `verdict` of `VULNERABLE`, `SUSPICIOUS`, or `SAFE` based on structural analysis (for example, a `HostnameVerifier.verify()` body that unconditionally `return`s `true` is `VULNERABLE`; a `TrustManager` check method with an empty body is flagged via `certificate_empty_trust_check`; a check that genuinely delegates to a real validation call is `SAFE`). **Relevant security features:** `certificate_hostname_verifier`, `certificate_return_true`, `certificate_trust_manager`, `certificate_empty_trust_check`, `certificate_exception_validation`, `certificate_default_verifier`, `webview_ssl_error`, `webview_handler_proceed`, `webview_handler_cancel` (9 of the 23 features). **ML classification:** the `v0`/`v1` probability pair from the same production booster. **Supporting evidence:** the Decision Engine weights a confirmed certificate vulnerability at `+2.0`, a suspicious/incomplete check at `+0.6`, and a confirmed-safe check at `−1.5`. **Explanation/remediation:** `generate_explanation_sentences()` produces sentences such as "HostnameVerifier.verify() unconditionally returns true." only when `certificate_return_true` is actually set for this request, and `chatbot_logic.py`'s fixed `CWE_295_EXPLANATION` text describes the standard fix (letting certificate/hostname validation run its real, default checks) for conversational questions.

As with CWE-89, this chapter does not claim perfect detection: structural analysis of a `HostnameVerifier`/`TrustManager` implementation can only reason about the patterns `dataflow.py` is written to recognise, and a sufficiently unusual implementation could fall outside what the analyzer classifies confidently.

## 6.12 IntelliJ/Android Studio Plugin Implementation

The plugin communicates with the backend exclusively through `APIClient.kt`, which defines Kotlin data classes (`ScanRequest`, `ScanResponse`, `Detection`, `DataFlowFinding`, `DecisionReason`, `ShapFeature`, and the `/developer/scan` batch equivalents) that mirror the backend's real JSON response shapes field-for-field — the file's own comments record that these shapes were checked against `app.py`/`predictor.to_developer_response()` directly rather than inferred. Requests are issued with OkHttp and parsed with Gson. Every field added after the plugin's initial version is declared nullable in these data classes, so a response from an older backend, or from `/predict`'s empty-input guard clause (which omits several fields), still parses successfully rather than throwing a deserialization error.

`plugin.xml` registers `CodeSentinelAnnotator` as an `ExternalAnnotator` for Java, Kotlin, and (for two specific filenames) XML, and registers the tool window, intention, and quick-fix classes described below.

## 6.13 Real-Time Code Inspection Implementation

**Figure 6.4. Plugin-to-Backend Communication.** *(figure_6_4_plugin_backend_communication.png)*

`CodeSentinelAnnotator` implements the IntelliJ Platform's three-method `ExternalAnnotator<FileScanData, List<LineScanResult>>` contract. `collectInformation()` runs on the UI thread, checks the file's language id (only `java`, `kotlin`, and — for `AndroidManifest.xml`/`network_security_config.xml` specifically — `xml` are scanned), and builds a `FileScanData` containing the whole file's text and a `LineData` entry (index, text, character offsets) for every line. `doAnnotate()` runs on a background thread and is the only place this class performs network I/O: it calls `APIClient` to `POST /predict` with the file's text, then maps the backend's `ScanResponse.detections` into a `List<LineScanResult>`, each carrying the vulnerability type, confidence, character offsets, and (Phase 4/5B additions) the whole-scan `severity`, `predictionModel`, `decision`, and `decisionEvidence`, plus the SHAP top features and raw security-feature values, so the tooltip can render this richness without a second request.

`apply()` runs back on the UI thread and calls `AnnotationHolder.newAnnotation()` for each `LineScanResult` — but, as already established architecturally in Chapter 5 and confirmed here at the implementation level, only for results the backend actually reported as vulnerable; a `SUSPICIOUS_REVIEW` decision produces a `ScanResponse` with `vulnerable == false` and therefore no call to `newAnnotation()` for that finding. Tooltip text is rendered as HTML, and an internal `escapeHtml()` helper escapes `&`, `<`, `>` in code/explanation text before it is interpolated, since unescaped generics syntax (e.g. `List<String>`) would otherwise silently break the tooltip's HTML rendering — a concrete implementation detail, not an architectural one, that was necessary because the underlying finding text can contain arbitrary source-code snippets.

A module-level `ConcurrentHashMap` cache and a `scanning` `ConcurrentHashMap`-backed set (declared as companion-object state on `CodeSentinelAnnotator`) avoid re-issuing a backend request for a file that is already being scanned or was scanned very recently, which is an implementation-level performance consideration for a real-time, keystroke-driven annotator rather than an architectural one.

## 6.14 Quick Fix and Re-Scan Implementation

Quick Fix implementation follows the locator/action split described architecturally in Chapter 5. `SqlFixLocator.kt` and `CertificateFixLocator.kt` implement the "is this safe to rewrite" decision by inspecting the actual PSI structure of the flagged expression (for example, `SqlFixLocator` uses `SqlConcatenationAnalyzer.kt` to determine whether a flagged SQL string has a sufficiently simple, single-level concatenation shape); where a locator returns a positive result, `SafeSqlQuickFixJava.kt`/`SafeSqlQuickFixKotlin.kt` or `SafeHostnameVerifierQuickFixJava.kt`/`SafeHostnameVerifierQuickFixKotlin.kt` perform the actual PSI expression rewrite inside a write action. `CertificateFixAnalyzer.kt` plays the equivalent structural-analysis role for certificate-validation fixes that `SqlConcatenationAnalyzer.kt` plays for SQL fixes.

After a Quick Fix is applied, `FixVerificationRunner.kt` triggers a genuine asynchronous re-scan of the modified file through the same `APIClient`/backend path used by real-time annotation — the "did the fix work" answer is a freshly-computed backend decision on the post-fix code, not an assumption that the rewrite necessarily changed the outcome. Batch/project-wide scanning is implemented separately in `ProjectFileCollector.kt`, which gathers eligible files and drives `MyToolWindow` through a single `POST /developer/scan` request rather than one request per file; `MyToolWindow.kt` maintains one shared, in-memory findings list populated from either the real-time annotator or a batch scan, with jump-to-source navigation implemented against the real PSI/file offsets already computed by whichever path produced the finding. `ShowFindingDetailsIntention.kt` implements `IntentionAction` with `startInWriteAction() = false` — it is bound to one specific finding at construction time and, on invocation, only calls `MyToolWindow.showFinding()`; it does not modify code, which keeps it a strictly separate, unrelated concern from the Quick Fix classes.

The functionality described in this and the preceding two sections is implemented in the plugin and exercised by 55 passing Kotlin tests, including a headless `BasePlatformTestCase` integration test that drives these real classes against the real backend; however, certain visible GUI behaviours — for example, a human directly observing an annotation, tooltip, or Quick Fix render inside a live, on-screen IDE window — remained subject to the documented live-validation limitations described in Section 6.23, and this chapter does not claim that kind of visual UI validation was performed beyond what is explicitly recorded there.

## 6.15 Flutter Mobile Application Implementation

**Figure 6.5. Flutter-to-Backend Communication.** *(figure_6_5_flutter_backend_communication.png)*

`ApiClient` (`lib/core/api_client.dart`) implements all API communication behind two methods, `get()` and `post()`, both of which build headers through a private `_headers()` helper that attaches `Authorization: Bearer <token>` whenever the injected token-provider callback returns a non-empty token, and both of which route through a shared `_send()` implementation. `_send()` wraps the actual `http.Client` call, catching `TimeoutException`, `SocketException`, and `http.ClientException` and re-throwing all three as a single `NetworkException`; on a response, it attempts `jsonDecode()` defensively (falling back to `null` on a decode failure rather than throwing) and then branches on the HTTP status code: `200`/`201` return the decoded body; `401` throws `UnauthorizedException` (using the server's own `detail` message when present); `404` throws `NotFoundException`; `400`/`422` throw `ValidationException`; anything else throws `ServerException`. Both `http.Client` and the token-provider function are constructor-injected, which is what allows the project's own tests to substitute `http.testing.MockClient` and a fake token supplier without touching a real network connection or real secure storage.

Authentication and session state are implemented in `AuthRepository` (`ChangeNotifier`), which is the only class permitted to read or write the persisted token, delegated to `SecureTokenStorage` (`lib/core/secure_token_storage.dart`), a thin wrapper around `flutter_secure_storage` with a single fixed storage key. `restoreSession()` is called once at startup to read any previously-stored token back into memory (never logging the token itself), so a user is not required to log in again on every app launch; `login()` persists a freshly-issued token and notifies listeners; `logout()` and `handleUnauthorized()` (called when any API call surfaces an `UnauthorizedException`) both clear the in-memory and persisted token and notify listeners, which is what routes the UI back to the login screen on an expired or invalid session rather than silently retrying with a dead token.

Security-related screens (`SearchApplicationScreen`, `ApplicationDetailsScreen`, `DeviceCompatibilityScreen`) each depend on a repository (`AppsRepository`, `DeviceProfileRepository`) rather than an API service directly, and render the typed exceptions surfaced by `ApiClient` through the shared `state_views.dart` widgets rather than each screen implementing its own error UI.

## 6.16 Authentication and Session Management

Backend authentication is implemented in `db/security.py`. Passwords are hashed with Argon2 (`argon2-cffi`'s `PasswordHasher`) for all new and updated passwords; `verify_password()` additionally recognises the project's legacy 64-character SHA-256 hex-digest scheme, returning `needs_upgrade=True` on a successful legacy match so `db/crud.py`'s `authenticate_user()` can transparently re-hash and persist the password with Argon2 at the moment of a successful login — a standard rolling migration, since a one-way hash cannot be batch-converted without the plaintext password. JWTs are signed with `PyJWT` using `HS256` and a server-side `JWT_SECRET` read from the environment (the application raises `JwtNotConfiguredError` with a clear remediation message if this is missing, rather than silently issuing an unsigned or default-secret token); tokens carry `sub` (user id), `email`, `iat`, and `exp` (default 30-day expiry, configurable via `JWT_EXPIRE_MINUTES`).

`get_current_user()` in `app.py` is the single dependency every protected route uses: it requires a well-formed `Authorization: Bearer` header, decodes the token via `decode_access_token()`, and distinguishes an expired token (`ExpiredSignatureError` → 401 "Token expired.") from a structurally invalid one (`InvalidTokenError` → 401 "Invalid token.") from a token whose subject no longer exists in the database (401 "User no longer exists."), before resolving a real `models.User` row. On the Flutter side, session management is implemented as described in Section 6.15: `AuthRepository` owns the in-memory session state, `SecureTokenStorage` owns persistence, and `ApiClient` only ever asks `AuthRepository` (via the injected token-provider callback) for the current token value — it never reads storage directly.

## 6.17 MySQL Database Implementation

The database connection is implemented in `db/session.py` (not modified for this chapter), which exposes `get_db()` as a FastAPI dependency yielding a SQLAlchemy `Session` per request and `check_connection()` for the startup liveness check described in Section 6.4; `DatabaseNotConfiguredError` is raised when the required connection configuration is absent, giving the centralised exception handler in `app.py` a specific, nameable failure mode rather than a generic error.

`db/models.py` defines the ten SQLAlchemy models already catalogued architecturally in Chapter 5 (`User`, `Application`, `AppVersion`, `Scan`, `Vulnerability`, `MLPrediction`, `RecommendationRecord`, `AlternativeApp`, `ChatHistory`, and a standalone `SecurityTip`), with relationships and cascade behaviour declared via SQLAlchemy's `relationship()`/`ForeignKey` constructs. `db/crud.py` implements every read and write against these models; no route in `app.py` issues SQL or touches a model class directly. Two implementation patterns recur throughout `db/crud.py` and are worth naming explicitly because they shape correctness: functions that participate in a larger, multi-step transaction (e.g. `get_or_create_application()`, `get_or_create_app_version()`, `create_scan()`, `add_vulnerability()`) call `db.flush()` rather than `db.commit()`, leaving the final commit to the top-level caller (`persist_apk_scan()`) so a failure partway through leaves nothing partially committed; and several "get or create" functions apply a "never overwrite a real value with a blank one" rule when merging new data into an existing row (for example, `get_or_create_application()` only fills in `category`/`developer`/`icon_url` when the existing row does not already have a real value).

Authentication-related data (`User.password_hash`, queried by `authenticate_user()`) never leaves `db/crud.py`/`db/security.py` as plaintext or a reversible value. Application/security data is written by `persist_apk_scan()`, which — as one transaction — creates or updates the `Application` and `AppVersion` rows, creates the `Scan` row, and creates zero or more `Vulnerability` rows strictly from `apk_scanner.py`'s real `detections`/`malicious_urls` findings (never a fabricated finding), plus one `RecommendationRecord` derived from the scan's actual risk level. Chat history is implemented by `save_chat_message()` (an unconditional insert, called by `POST /ai-chat` whenever the request carries a `user_id`) and, since Phase 14C, `get_user_chat_history()` (Section 6.19).

## 6.18 Chatbot Implementation

**Figure 6.6. Chatbot Request and Response Flow.** *(figure_6_6_chatbot_request_response_flow.png)*

The Flutter chatbot UI (`SecurityChatScreen`) sends each message through `ChatRepository`, which wraps `ChatApiService`, which issues `POST /ai-chat` with the message text and, where the chat was opened from a specific application's context, that application's real `app_id`. `chatbot_logic.py` implements `generate_chat_response()` as the single backend entry point: it first calls `_strip_legacy_context_prefix()` (recovering the user's real question from an older client-side prefix format still supported for backward compatibility), then `_classify_intent()`, a deterministic function that checks the lower-cased message text against fixed phrase lists in a specific order — CWE-89 explanation, CWE-295 explanation, compatibility, recommendation explanation, why-risky, what-to-do, falling back to a general application-name lookup (`app_lookup`) if nothing matches.

CWE-89/CWE-295 questions return fixed, hand-written reference text (`CWE_89_EXPLANATION`/`CWE_295_EXPLANATION`) that never varies per application, since these are stable MITRE definitions. The `why_risky`, `what_to_do`, `explain_recommendation`, and `compatibility` intents require a real, resolved assessment: when `app_id` is supplied, `database.get_app_assessment_by_id()` is called, and the corresponding `answer_*()` function (`answer_why_risky()`, `answer_what_to_do()`, `answer_recommendation_explanation()`, `answer_compatibility_question()`) builds its response strictly from that assessment's real stored fields (`risk_level`, `vulnerability_types`, `recommendation_reason`, `min_sdk_version`), returning an explicit "I don't have a verified security assessment" message when no assessment exists rather than fabricating one. Suggestion chips implemented in the Flutter UI map directly onto these intents; the `why_risky` intent's phrase list was extended in an earlier validation phase specifically to also match the chip's own wording ("Why is this app high risk?"), after live device testing found the original phrase list did not.

Every exchange — regardless of which intent matched — is persisted via `database.save_chat_message(user_id, message, reply)` whenever the request carries a `user_id`, implementing the write side of chat history.

## 6.19 Chat History Implementation

**Figure 6.7. Chat History Retrieval Flow.** *(figure_6_7_chat_history_retrieval_flow.png)*

`GET /user/chat-history` is implemented in `app.py` as `get_authenticated_user_chat_history()`, depending on the same `get_current_user()` JWT dependency used by `GET /user/history`, and returning `{"history": crud.get_user_chat_history(db, current_user.id)}`. It is JWT protected, user-specific, and retrieved strictly through the authenticated user's identity: `current_user.id` is derived from the verified token payload's `sub` claim, never from any client-supplied identifier, so the endpoint structurally cannot return another user's chat transcript. `crud.get_user_chat_history()` queries the `chat_history` table filtered by `user_id`, ordered `created_at.asc()` (oldest first, since a transcript is read start-to-finish, unlike the newest-first scan history), and returns each row's `id`, `question`, `answer`, and ISO-formatted `created_at`.

On the Flutter side, `ChatApiService.getHistory()` calls `GET /user/chat-history` and expands each returned row into two `ChatMessage` objects (the question, marked `fromUser: true`, and the answer, marked `fromUser: false`, both timestamped from the same `created_at`), and `ChatRepository.getHistory()` exposes this to the UI layer unchanged. `SecurityChatScreen` calls this from `initState()` only when `AuthRepository.currentUser?.id` is non-null, with a silent fallback (no crash, no blocking error dialog) when no user is signed in or the request fails, matching the rest of the application's typed-exception handling pattern. This implementation is covered by seven new backend tests (message-stored, own-history-retrieval-in-order, cross-user isolation, empty history, and three unauthorised-access cases, all in `tests/test_chat_history.py`) and two new Flutter repository tests; live Android UI observation of this exact flow was not separately performed and is reported using the status established in Section 6.23, not upgraded to a passing live result.

## 6.20 API Integration

Rather than re-describing every one of the twenty routes already catalogued architecturally in Chapter 5, this section illustrates integration through representative examples across each category. **Authentication APIs** (`POST /register`, `POST /login`) implement the credential-verification and token-issuance flow described in Section 6.16, with `/login` additively returning a `token` field alongside its pre-existing `message`/`user` fields so older clients reading only the legacy shape are unaffected. **Security analysis APIs** (`POST /predict`, `/developer/predict`, `/developer/scan`, `/developer/explain`, `/developer/rescan`, `/decision`) all integrate with exactly one function, `predictor.predict_code()`, differing only in how the API layer reshapes its output (`to_developer_response()`, `to_explain_response()`, or the raw `predict_code()` shape for backward compatibility). **Application APIs** (`GET /apps/search`, `/apps/{app_id}`, `/apps/{app_id}/security`) integrate with `db/crud.py` and, for the security endpoint, additionally with `compatibility.evaluate_full_compatibility()` to attach a device-independent compatibility summary. **Compatibility APIs** (`POST /apps/{app_id}/compatibility`) combine a caller-supplied `DeviceProfile` with the application's own server-stored manifest metadata, never trusting a client's claim about an app's own `minSdkVersion` or required features. **Chatbot APIs** (`POST /chat`, `POST /ai-chat`) integrate with `chatbot_logic.py` as described in Section 6.18. **The chat-history API**, `GET /user/chat-history`, integrates with `db/crud.py` as described in Section 6.19, and is explicitly included here as the newest addition to the API surface.

## 6.21 Error Handling and Validation

Error handling is implemented at three levels. At the framework level, FastAPI's Pydantic request models reject a structurally invalid request body (missing required fields, wrong types, or — for `BatchScanRequest` — a file list outside the declared `min_length=1`/`max_length=200` bounds) with a `422` response before any route handler code runs. At the application level, `app.py` registers the three exception handlers described in Section 6.4: unhandled exceptions become a `500 {"error": "internal_error", ...}` response with the real exception logged server-side (never a raw stack trace returned to the caller); `HTTPException`s raised deliberately by route handlers (e.g. `404` for an unknown `app_id`, `400` for an empty search query, `413` for an oversized APK upload) are normalised into the same `{"error": "request_error", "detail": ...}` shape; and a missing/unreachable database surfaces as an explicit `503 {"error": "database_not_configured", ...}` rather than a generic failure. At the authentication level, `get_current_user()` implements three distinct `401` cases (missing/malformed header, expired token, structurally invalid token, and a token for a user that no longer exists) rather than a single undifferentiated "unauthorized" response.

Invalid or unsupported input is handled close to where it is produced: `_guarded_predict()` rejects any single file over 200KB before it reaches feature construction; `/upload-apk` rejects a non-`.apk` filename immediately and enforces a 100MB streamed-upload limit, raising `413` mid-stream rather than after buffering the whole file. The chatbot's fallback behaviour is itself a form of input handling: an unrecognised or ambiguous message falls through `_classify_intent()`'s `app_lookup` branch, and if no application name can be extracted from the text, `generate_chat_response()` returns the fixed `GREETING` text rather than raising an error or returning an empty response. On the Flutter side, every error surfaced by `ApiClient` is one of five typed exceptions, and screens render each type through the shared `state_views.dart` widgets rather than exposing a raw error string.

## 6.22 Security and Privacy Considerations

The implementation-level security measures actually present in the codebase are: JWT authentication (Section 6.16), scoped to exactly the three routes that expose a specific user's own private data (`/user/history`, `/user/chat-history`, and the login flow that issues the token both depend on); Argon2 password hashing with a safe, lazy migration off the legacy SHA-256 scheme; user-specific chat history, enforced structurally by deriving `user_id` from the verified JWT rather than from any request parameter, so cross-user access is not merely a convention but a property of how the query is constructed; Pydantic request-model validation at the API boundary, implemented for every route that accepts a body; a clean separation between client and backend, in which neither the plugin nor the Flutter application holds the production model, the feature pipeline, or any database credential — both reach the backend only through its public HTTP contract; and, for vulnerability analysis specifically, the system never returns a fabricated finding, score, or compatibility verdict — a value that cannot be legitimately computed (an un-assessed application's security score, a device-compatibility field with no device profile supplied) is returned as `null`/`NOT_AVAILABLE` rather than synthesised.

This chapter does not claim encryption mechanisms — such as at-rest database encryption or end-to-end message encryption — that were not located in the inspected source; the JWT itself is stored on the mobile client using `flutter_secure_storage`, which is the platform-appropriate secure storage mechanism for a bearer token on Android, but this chapter does not characterise this as full at-rest database encryption, which is a separate, unverified concern outside the scope of the modules inspected for this chapter.
