# Final Limitations

- **Small labelled dataset.** 1,687 raw rows, 1,128 after conflicting-label exclusion, split into 791/169/168. This is a small dataset by ML standards; results should be read as indicative, not as population-level guarantees.
- **No application-level split.** The dataset carries no application/project identifier, so the train/validation/test split is grouped by normalized-code template (`normalize_code()`), not by source application. Generalization to genuinely unseen applications is not directly measured.
- **Conflicting labels.** 559 rows (270 groups) were excluded because the same normalized code template carried more than one distinct label elsewhere in the raw data — real annotation noise in the source dataset, not a modeling artifact.
- **DL models are supplementary research comparisons.** LSTM and CodeBERT were evaluated on the same frozen split for a fair comparison, but neither is integrated into the production pipeline. Their input representations differ from the classical ML models' TF-IDF/count/security-feature pipeline (LSTM uses learned embeddings over a code-aware token sequence; CodeBERT uses a pretrained transformer's own tokenizer) — this is a real architectural difference, not an oversight.
- **CodeBERT is not production.** CodeBERT shows competitive overall performance and the best CWE-89 recall among the five models, but remains a research finding, not a deployed component.
- **LSTM from-scratch limitations.** Trained from scratch (not pretrained) on a small dataset; shows visible overfitting and the lowest macro-F1 among the five evaluated models.
- **Decision Engine robustness is INCONCLUSIVE**, not confirmed. The Balanced research candidate's cross-split FNR advantage over raw XGBoost is SUPPORTED (H1), but its threshold stability under perturbation is INCONCLUSIVE (H2) and its CWE-89/CWE-295 asymmetry hypothesis is NOT SUPPORTED (H3) — combined, this yields an overall INCONCLUSIVE robustness classification and a "PROMISING BUT MORE DATA REQUIRED" production-candidate decision. The Balanced thresholds remain NOT DEPLOYED.
- **No human-observed, pixel-rendered IntelliJ GUI validation in Phase 12/13/14A.** No screenshot was ever captured of the plugin running in a visible IDE window, and no Alt+Enter/Quick-Fix-preview interaction was performed by a human or by mouse/keyboard automation. Phase 14A's first attempt was resource-blocked (2.70-3.12GB free RAM of 15.75GB, with active Windows memory compression, plus 0.43GB free on C:); a second attempt, after resources recovered to 7.43GB free RAM / 7.57GB free C:, found the real remaining blocker was NOT resources but a tooling gap: this agent has no screen-capture or GUI-interaction capability at all, independent of the machine's state. In place of pixel-level validation, 9 new tests (`LiveAnnotatorIntegrationTest.kt`) drive the REAL registered `CodeSentinelAnnotator`/`ShowFindingDetailsIntention`/`SqlFixLocator`/`CertificateFixLocator` classes inside a real (headless) IntelliJ Platform test fixture against the REAL running FastAPI backend - all 9 pass, with real severities/confidences/decisions/diffs/re-scan results captured as evidence. This is a genuine escalation in rigor over plain unit tests, but it is explicitly NOT a substitute for someone actually watching the rendered editor, tooltip, and Quick-Fix preview UI. See `phase14a_plugin_validation_attempt.md` (first attempt) and `phase14a_second_attempt.md` (second attempt, headless-platform-test evidence).
- **Android emulator validation status by phase (kept distinctly provenanced, never merged).** Phase 12/13: not connected (`flutter devices` showed only Windows desktop, Chrome, and Edge; `adb` was not on PATH) - NOT VALIDATED. **Phase 14B: performed for real** - an existing Pixel_4 AVD (Android 16 / API 36, x86_64) was cold-booted and used to install and drive a real debug build against the real FastAPI backend and real MySQL. Registration, login, wrong-password, session-restore, and logout were all verified with real HTTP calls and real database writes; Search/Application Details/Security Assessment/Compatibility/Alternatives/History were verified against real backend data. A real chatbot bug was found and fixed during this session (see below). Some sub-cases were not exercised (Search "unknown app"/"network error", Compatibility INCOMPATIBLE/NOT_AVAILABLE scenarios, the full chatbot question list, chat-history reload, and APK upload - the last because no such feature exists in this app's UI at all). Full detail in `phase14b_android_validation.md`.
- **Screenshots.** Phase 12/13 had none (no live session was run). **Phase 14B has 61 real screenshots** captured via `adb shell screencap`, covering login/register/dashboard/search/details/compatibility/alternatives/history/chatbot/logout, stored under `dualvulndroid_flutter/phase14b_screenshots/`; none were fabricated, and password fields were confirmed masked before capture.
- **A real, live-discovered chatbot bug (found and fixed in Phase 14B).** The Flutter app's own built-in suggestion chip reads "Why is this app high risk?", which the backend's keyword-based intent classifier did not originally match (it only matched "risky"/"risk"-suffixed phrasings), so tapping that exact chip silently returned the generic greeting instead of a real, grounded answer. Fixed by adding "high risk" (and a couple of close synonyms) to the matched phrase list in `chatbot_logic.py`; verified live on the device after a backend restart, and locked in with a new regression test. This is the only application-code change made across the Phase 14A/14B live-validation sessions.
- **Deterministic chatbot intent matching, not full NLU.** The chatbot classifies intent via keyword matching (consistent with the project's existing non-LLM design), not a language model. Questions phrased very differently from the tested patterns may fall through to the generic greeting rather than being understood.
- **Hardware compatibility limitations.** Compatibility answers (chatbot and `compatibility.py`) depend on a real `min_sdk_version` having been extracted from the APK manifest at scan time; when that value is missing, the system reports `NOT_AVAILABLE` / says so honestly rather than guessing. RAM-based compatibility is not evaluated in chat answers, since no reliable source of an app's minimum RAM requirement exists in this project.
